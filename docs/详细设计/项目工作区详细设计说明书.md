## 1. 引言

### 1.1 编写目的

本文档对软件测试平台中的**功能测试模块**进行详细设计，定义数据结构、接口规范、业务逻辑、前端组件及交互流程，为开发实现提供完整依据。

### 1.2 范围

功能测试模块面向**业务用户**，在已选定的项目内提供测试用例管理、测试评审、测试计划及缺陷管理功能。所有操作限定在当前活跃工作空间和项目上下文中，项目上下文通过请求头 `X-Active-Project` 传递。

枚举取值（业界惯例的语义化 snake_case 命名）：

- **bug_type**：`code_error` 代码错误、`ui_improvement` 界面优化、`design_defect` 设计缺陷、`configuration` 配置相关、`installation` 安装部署、`security` 安全相关、`performance` 性能问题、`standard_spec` 标准规范、`other` 其他。
- **resolution**：`fixed` 已修复、`by_design` 设计如此、`duplicate` 重复缺陷、`external` 外部原因、`cannot_reproduce` 无法重现、`deferred` 延期处理、`wont_fix` 不予解决。

状态机（禅道式四态模型）：

```
                    ┌──────────┐
                    │  active  │
                    └────┬─────┘
                  ┌──────┴──────┐
                  ▼              ▼
            ┌──────────┐  ┌──────────┐
            │ resolved │  │ rejected │
            └─────┬────┘  └─────┬────┘
                  │              │
                  └──────┬──────┘
                         ▼
                   ┌──────────┐
                   │  closed  │
                   └────┬─────┘
                        │
                        ▼
                     active（重开）
```

- **解决** active → resolved：必填 resolution + 备注说明；resolution=duplicate 时必填 duplicate_of_bug_id（校验存在、非自身且同项目）；记录 resolved_by/resolved_at；**处理人回设为创建人**（由创建人验证）。
- **拒绝** active → rejected：必填说明；处理人回设为创建人；记录 rejected_by（拒绝人），重开时处理人回设给拒绝人。
- **关闭** resolved/rejected → closed：必填说明；记录 closed_by/closed_at。
- **重开（激活）** resolved/rejected/closed → active：必填说明；reopen_count+1、last_reopened_at=now，清空 resolution/duplicate_of_bug_id/resolved_by/resolved_at/rejected_by/closed_by/closed_at；**处理人流转**：若从 resolved 重开则回设给解决人，若从 rejected 重开则回设给拒绝人，无可追溯的修复/拒绝人时保持原处理人不变。
- **确认**：独立操作，仅 active 且未确认时可执行，confirmed=true，写 bug_log。

## 3. 接口详细设计

### 3.1 通用约定

- 项目内接口基础路径：`/api/project`
- 认证：`Authorization: Bearer <token>`
- 业务请求头：必须带 `X-Active-Project`
- 命名风格：camelCase
- 分页：`page`、`pageSize` → `{ records: [], total: number }`
- 通用响应：`{ "code": 200, "message": "success", "data": {} }`

### 3.2 项目工作台接口

#### 3.2.1 获取项目工作台数据

- **路径**：`GET /api/project/dashboard`

- **说明**：返回当前项目的概览统计数据。

- **响应**：
  
  ```json
  {
  "caseCount": 256,
  "activeReviewCount": 3,
  "activePlanCount": 2,
  "openBugCount": 12,
  "recentReviews": [
    { "id": 1, "title": "登录模块评审", "status": "completed", "createdAt": "2026-07-01T10:00:00Z" }
  ],
  "recentPlans": [
    { "id": 1, "name": "功能测试计划", "status": "in_progress", "createdAt": "2026-07-05T09:00:00Z" }
  ]
  }
  ```

### 3.3 测试用例管理接口

#### 3.3.1 获取模块树

- **路径**：`GET /api/project/modules`
- **响应**：直接返回树形数组，每个节点包含 id、name、type、children。

#### 3.3.2 创建模块节点

- **路径**：`POST /api/project/modules`
- **请求体**：`{ "parentId": null, "type": "directory", "name": "新目录" }`
- **校验**：同父节点下名称唯一。
- **文档类型特殊处理**：当 `type=document` 时，事务中创建文档节点并自动创建默认根节点（title 与文档 name 一致，type='normal'）。
- **响应**：创建后的模块节点信息，状态码 201。

#### 3.3.3 更新/删除模块节点

- **路径**：`PUT/DELETE /api/project/modules/:id`
- 更新：可修改 name；也用于拖拽移动——请求体中 `targetIndex` 非空时视为移动操作，`parentId` 为目标父目录（空表示根层级），`targetIndex` 为目标层级下的位置下标。

#### 3.4.1 获取评审列表

- **路径**：`GET /api/project/reviews`

- **参数**：`status`（可选，new/in_progress/completed）、`keyword`（可选，标题模糊匹配）、`page`、`pageSize`

- **响应**：
  
  ```json
  {
  "records": [
  ```

- **进度字段**：`totalAssociated` 为关联用例总数，`passed` 为通过数；`progressPercent` =（总数 − 待评审数）/ 总数，`passRate` = 通过数 / 总数，均为百分数保留两位。后端按本页评审 ID 批量查询关联用例快照聚合计算，避免逐行 N+1。

#### 3.4.2 创建评审

- **路径**：`POST /api/project/reviews`

- **请求体**：
  
  ```json
  {
  "title": "登录模块评审",
  "description": "...",

  ]
  }
  ```

- **处理**：生成模块快照和节点快照（完整拷贝节点属性），标记 is_associated，初始化评审状态为 new（待评审），发起人默认为当前用户；首次提交标记后自动转入 in_progress。

#### 3.4.3 获取评审详情

- **路径**：`GET /api/project/reviews/:id`
- **响应**：基本信息 + participantIds + 快照信息（涉及的文档数量等）。

#### 3.4.4 获取评审快照树

- **路径**：`GET /api/project/reviews/:id/modules`
- **参数**：`documentId`（可选，按文档过滤）
- **响应**：裁剪后的模块树 + 节点树。节点部分以嵌套的根节点对象形式返回（结构与 3.3.4 一致），每个节点包含完整拷贝属性及 lastMark、associated 等快照特有字段。

#### 3.4.5 提交评审记录

- **路径**：`POST /api/project/reviews/:id/records`

- **请求体**：
  
  ```json
  {
  "snapshotNodeId": 5001,
  "operationType": "mark",
  "mark": "pass",
  "comment": "步骤清晰"
  }
  ```

- **处理**：新增 test_review_record，更新 test_review_node_snapshot 的 last_mark、last_reviewer_id、last_reviewed_at。仅 type='case' 节点可标记，所有节点均可评论。

- **mark 取值**：`pass` / `fail` / `pending`。pending 表示重置回待评审，仅为 API 交互值，落库时 last_mark 置 NULL（即初始态）；前端工具栏提供“通过/不通过/待评审”三态标记，标记结果以徽标形式回显在节点右侧。

- **状态校验**：评审已完成（completed）时拒绝，返回语义化错误码 1000011026（“评审已完成，无法执行该操作”）；待评审（new）状态下首次标记成功后评审自动转入 in_progress。

#### 3.4.6 获取节点评审记录

- **路径**：`GET /api/project/reviews/:id/nodes/:nodeId/records`
- **响应**：该节点的所有标记和评论历史，按时间排序。

#### 3.4.7 完成评审

- **路径**：`POST /api/project/reviews/:id/complete`
- **权限**：仅发起人。
- **前端校验**：详情页要求待评审数与不通过数均为 0（全部通过）才允许提交，否则按钮置灰并提示；列表页的[完成]操作经确认后直接调用，不做全部通过门槛校验。
- **处理**：状态变更为 completed，快照冻结。

#### 3.4.8 同步最新用例

- **路径**：`POST /api/project/reviews/:id/sync`
- **权限**：发起人，评审未完成（new/in_progress）；已完成快照已定格，返回错误码 1000011026。
- **处理**：根据 original_node_id 匹配当前节点，更新快照属性；已删除节点标记 is_deleted=1；保留评审记录不变。前端同步成功后重新拉取快照并重载脑图。

#### 3.4.9 获取模块快照树

- **路径**：`GET /api/project/reviews/:id/module-tree`
- **响应**：模块快照树（目录/文档层级，含 id、parentId、name、type、sortOrder、children），供详情页左侧文档树展示与多文档切换（选中文档后以 documentId 调用 3.4.4 加载单文档快照脑图）。

#### 3.4.10 获取规划用例

- **路径**：`GET /api/project/reviews/:id/cases`
- **响应**：`[{ "documentId": "...", "caseIds": ["..."] }]`，以原始文档/节点 ID 表示当前关联的用例，供调整弹窗回显预选。

#### 3.4.11 调整规划用例

- **路径**：`PUT /api/project/reviews/:id/cases`
- **前置**：评审未完成（new/in_progress，不限发起人）；已完成返回错误码 1000011026。
- **请求体**：`{ "selectedNodes": [{ "documentId": "...", "caseIds": ["..."] }] }`（与创建评审的 selectedNodes 同构）。
- **处理**：差量更新快照——新增文档生成模块/节点快照；移除文档删除其快照并自底向上清理空目录快照（标记/评论记录保留作审计）；保留文档补全快照后新增的节点并按新选择重刷 is_associated（取消关联的节点保留已有标记，仅退出统计）。快照节点插入按父链先序递归执行，保证父子映射完整。

#### 3.4.12 删除评审

- **路径**：`DELETE /api/project/reviews/:id`
- **权限**：仅发起人，任意状态可删。
- **处理**：无物理外键，事务中显式级联删除评审记录、节点快照、模块快照后删除评审本体。

  ```json
  {
  ```
  ```json
  "title": "登录页面崩溃",
  ```

  ```json
  "reproSteps": "1. 打开登录页\n2. 点击登录按钮\n3. 页面白屏",
  "moduleId": "<uuid>",
  "keywords": "登录 白屏",
  "dueDate": "2026-07-20",
  "assigneeId": 2,
  "relatedCaseId": 101,
  "relatedPlanId": 5
  }
  ```

- **处理**：缺陷已关闭（closed）时拒绝编辑（错误码 1000012019），须先激活；修改 assigneeId 时校验其为当前工作空间成员；关联字段采用三态语义：null=不修改、空串=清空、UUID 串=更新；记录变更到 bug_log。

- **路径**：`GET /api/project/bugs/:id/logs`
- **响应**：按时间排序的操作记录列表。

#### 3.6.5 变更缺陷状态

- **路径**：`PATCH /api/project/bugs/:id/status`
- **请求体**：`{ "status": "resolved|rejected|closed|active", "resolution": "fixed", "duplicateOfBugId": "<uuid>", "comment": "变更说明" }`（resolution/duplicateOfBugId 仅 status=resolved 时使用，comment 在 reject/close/reopen 时必填）
- **处理**：按四态状态机校验流转合法性（active→resolved/rejected、resolved/rejected→closed/active、closed→active）；解决时 resolution 必填且需备注说明，resolution=duplicate 时 duplicateOfBugId 必填（校验存在、非自身且同项目），并自动置 confirmed=true（解决即视为确认），**处理人自动回设为创建人**；拒绝时 comment 必填，处理人回设为创建人，记录 rejected_by；关闭与重开时 comment 必填；重开时 reopen_count+1 并清空解决/关闭字段，**重开处理人流转**：已解决→回设给解决人，已拒绝→回设给拒绝人；写入 bug_log（RESOLVE/REJECT/CLOSE/REOPEN）。

#### 3.6.6 确认缺陷

- **路径**：`PATCH /api/project/bugs/:id/confirm`
- **处理**：仅 active 且未确认的缺陷可执行；confirmed=true，写入 bug_log。

#### 3.6.7 指派处理人

- **路径**：`PUT /api/project/bugs/:id/assign`
- **请求体**：`{ "assigneeId": "<uuid>" }`
- **处理**：缺陷已关闭（closed）时拒绝改派（错误码 1000012019）；校验处理人为当前工作空间成员，写入 bug_log。

#### 3.6.8 缺陷统计

- **路径**：`GET /api/project/bugs/statistics`
- **响应**：`{ "total": 10, "byStatus": {}, "bySeverity": {}, "byPriority": {}, "byAssignee": {}, "byReporter": {} }`

#### 3.6.9 上传附件

- **路径**：`POST /api/project/bugs/:id/attachments`
- **请求**：multipart/form-data，字段名 `file`，单文件上限 10MB。
- **处理**：缺陷已关闭时拒绝上传；文件落盘后写入 bug_attachment 与 bug_log。
- **响应**：附件信息 `{ "id", "fileName", "fileSize", "contentType", "uploader", "createdAt" }`。

#### 3.6.10 附件列表

- **处理**：缺陷已关闭时拒绝删除；逻辑删除附件记录并写入 bug_log。

## 4. 业务逻辑设计

### 4.1 文档创建与默认根节点

创建 type=document 的模块节点时，事务中插入 test_case_module 记录，并在 test_case_node 表中创建默认根节点（title 与文档名称相同，type='normal'，sort_order=0，parent_id 为 NULL）。此根节点作为文档脑图的唯一顶层节点，用户可在其下添加子节点并标记为不同用例类型。获取文档节点树时，该根节点作为顶层节点返回，其 children 包含所有用户创建的节点。

### 4.2 脑图实时协作

通过 WebSocket 连接 `/ws/documents/:docId`，客户端加入文档房间。操作消息包含 op（add_node、move_node、update_attrs、delete_node、update_layout）及 payload。服务端校验权限后更新 test_case_node 和 test_case_document_layout，广播给同房间其他用户。冲突处理使用节点 version 字段的乐观锁机制。脑图数据以嵌套树形结构在前端组件中渲染，保存时递归遍历节点树并更新数据库。

### 4.3 快照生成与裁剪

评审或计划创建时，递归复制所需路径的 test_case_module 和涉及文档的全部 test_case_node。节点所有字段原样复制到快照表，is_associated 根据用户选择的 caseIds 标记。裁剪展示时根据关联节点向上追溯祖先、向下加载后代，构建最小树，返回嵌套的根节点对象。

### 4.4 评审/执行记录与状态更新

每次提交记录时，事务中插入记录表并更新快照节点的最后状态字段。评审中仅用例节点可标记，所有节点可评论。执行中仅关联用例节点可标记执行结果，默认根节点不可执行。

### 4.5 同步最新用例

触发后批量对比原始节点与当前节点，更新快照属性；若原始节点不存在，快照节点 is_deleted=1。评审记录/执行记录不受影响，最终状态保留。

### 4.6 权限控制

所有接口校验用户是否属于当前项目所属的工作空间。评审操作仅发起人可完成/同步/删除，参与者均可提交记录。计划操作负责人可编辑、同步、完成/关闭、删除，执行人可提交执行记录。
