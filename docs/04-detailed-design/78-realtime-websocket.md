# 软件测试平台——WebSocket 实时通信详细设计

**文档版本**：V1.0
**日期**：2026-09-24
**状态**：起草中

---

## 1. 引言

### 1.1 编写目的

本文档定义平台 WebSocket 传输层的项目级接入方式，覆盖连接建立、一次性 Ticket、房间管理、消息信封、错误处理、生命周期、可观测性和前后端协作边界。

通用协议要求以 `docs/00-spec/20-contracts/03-realtime-protocol.md` 为唯一事实源；本文档只补充项目实现约束，不重新定义业务事件、Payload、协作算法或持久化语义。

### 1.2 适用范围

本文档适用于平台所有需要长连接的业务场景。当前已有的文档协作连接作为第一个接入适配器；其他业务场景复用同一连接、Ticket、房间和生命周期机制。

业务事件类型、字段、顺序、冲突处理和持久化规则必须放在对应业务详细设计中。通用传输层不得通过事件名称推断业务权限，也不得把业务异常当作传输层错误。

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| Ticket | 短时、一次性、绑定用户和连接范围的握手凭证 |
| 会话 | 服务端为一个已认证 WebSocket 连接分配的 `sessionId` |
| 房间 | 服务端按资源范围维护的广播隔离单元；客户端不能任意创建或加入 |
| 消息信封 | 文本 JSON 帧的统一外层结构 |
| 写入操作 | 可能改变服务端状态或触发持久化的业务事件；不等同于传输层 ACK |

## 2. 数据设计

### 2.1 会话数据

会话由框架的 `WebSocketSessionManager` 维护，业务层只读取和写入经过授权的会话属性。

| 字段 | 说明 |
| --- | --- |
| `sessionId` | 框架分配的连接标识，不作为业务资源 ID |
| `userId` | 握手认证后绑定的用户标识 |
| `resourceType` / `resourceId` | Ticket 允许访问的资源范围 |
| `connectedAt` / `lastSeenAt` | 连接建立和最近活动时间 |
| `connectionId` | 访问日志和指标使用的脱敏连接标识 |
| `protocolVersion` | 客户端协商的协议版本 |

会话属性不得保存明文 Access Token、密码、API Key 或完整业务 Payload。`userId`、`resourceId` 和 `sessionId` 写入日志前必须按安全规范脱敏。

### 2.2 Ticket 数据

Ticket 是目标连接凭证，不替代业务权限校验。Ticket 至少绑定以下信息：

| 字段 | 说明 |
| --- | --- |
| `ticketId` | 不可预测的随机标识；不暴露内部主键 |
| `userId` | 申请 Ticket 的用户 |
| `resourceType` / `resourceId` | 允许连接的资源范围 |
| `permissionSnapshot` | 申请时的连接范围或权限版本，不作为长期授权快照 |
| `expiresAt` | 过期时间 |
| `consumedAt` | 原子消费时间；为空表示未使用 |
| `originPolicy` | 适用的 Origin 策略标识 |

Ticket 存储在 Redis 等短期存储中，设置绝对过期时间。握手消费必须使用原子操作；重复消费、过期、用户不匹配或资源不匹配均拒绝连接。Ticket 明文不得写入普通日志、审计详情、指标标签或异常消息。

### 2.3 房间命名

房间名称由服务端根据已授权资源生成，推荐格式为：

```text
ws:{resourceType}:{resourceId}
```

客户端只能提出订阅意图，不能直接提交任意房间名称。服务端必须将订阅请求与 Ticket 的 `resourceType/resourceId` 比对，并在加入房间前完成资源授权。

同一用户的多标签页、重连和并发连接策略由部署配置明确；默认值和限制必须记录在运行配置中，不得由前端自行绕过。

### 2.4 指标和审计数据

服务端记录连接数、连接成功/失败原因、房间数、消息数量、字节数、发送延迟、断开原因、重连次数和权限失败次数。审计事件至少覆盖 Ticket 申请、握手成功/失败、订阅、取消订阅、权限拒绝和异常关闭。

## 3. 接口详细设计

### 3.1 Ticket 申请接口

业务资源对应的 Ticket 申请 URL 由业务详细设计定义；申请接口遵循以下通用契约：

```http
POST {resource-ticket-path}
Authorization: Bearer <access-token>
X-Active-Workspace: <workspace-id>
X-Active-Project: <project-id>
```

请求体为空。上下文只能通过请求头传递，资源自身 ID 只能作为资源路径或服务端已确定的业务范围使用，不得把活动上下文 ID 放入请求体。

成功响应的 `data`：

```json
{
  "ticket": "opaque-short-lived-ticket",
  "expiresAt": "2026-09-24T12:01:00Z",
  "path": "/ws/documents/018f..."
}
```

`ticket` 只用于随后的一次 WebSocket 握手，不得作为业务 API 的 Access Token。客户端不得缓存、打印或写入 URL 监控数据。

### 3.2 WebSocket 握手

当前浏览器连接适配器可使用以下形式提交 Ticket：

```text
wss://<host>/ws/{resourceType}/{resourceId}?ticket=<opaque-ticket>
```

查询参数中的 Ticket 仍是短时凭证，网关、访问日志、代理日志和错误日志必须按敏感字段脱敏。新客户端不得使用长期 Access Token 替代 Ticket；迁移期的旧 Token 方式仅作为兼容开关，并必须有下线期限。

握手处理顺序：

1. 校验路径格式和资源 ID；
2. 校验 `Origin` 是否在生产白名单内；
3. 原子消费 Ticket，并校验用户、资源范围和过期时间；
4. 重新加载用户状态、成员关系和资源权限；
5. 创建会话并绑定服务端生成的会话属性；
6. 将连接加入已授权房间；
7. 记录连接审计和指标；
8. 允许客户端发送订阅或业务消息。

握手任一步骤失败都必须在加入业务房间前拒绝连接；不得先建立房间再异步补鉴权。Origin 缺失、生产环境使用通配符或 Ticket 无效时均按安全策略拒绝。

### 3.3 文本 JSON 消息信封

平台文本消息使用以下结构：

```json
{
  "type": "event",
  "requestId": "request-id",
  "version": 1,
  "payload": {}
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 是 | 控制消息或业务事件类型 |
| `requestId` | 建议 | 幂等、追踪和 ACK 关联 |
| `version` | 是 | 协议或业务 Payload 版本 |
| `payload` | 按类型 | 业务数据，由对应详细设计定义 |

控制消息可使用 `subscribe`、`unsubscribe`、`ack`、`ping`、`pong` 和 `error`。控制消息不得携带未声明的业务副作用；业务事件必须使用独立类型并由业务详细设计定义权限、幂等和持久化规则。

### 3.4 二进制消息

二进制帧只承载已登记的高频或二进制协议。服务端不解析未登记的业务二进制内容，只执行大小、频率、连接范围和写权限校验后按房间转发。

二进制帧必须定义：

- 最大字节数；
- 编码和版本；
- 是否允许持久化；
- 是否要求编辑权限；
- 慢消费者和发送背压策略；
- 断开和重连时的处理方式。

### 3.5 错误帧

传输层错误统一使用稳定字符串码：

```json
{
  "type": "error",
  "requestId": "request-id",
  "code": "WS_PERMISSION_DENIED",
  "message": "无权执行该操作",
  "version": 1
}
```

| 错误码 | 含义 | 典型处理 |
| --- | --- | --- |
| `WS_AUTH_FAILED` | Ticket、身份或 Origin 校验失败 | 拒绝握手或关闭连接 |
| `WS_PERMISSION_DENIED` | 无资源订阅或写入权限 | 返回错误帧，不广播、不持久化 |
| `WS_PROTOCOL_INVALID` | 消息结构、版本或类型非法 | 返回错误帧，必要时关闭连接 |
| `WS_MESSAGE_TOO_LARGE` | 帧超过大小限制 | 拒绝该帧并计数 |
| `WS_RATE_LIMITED` | 消息或连接频率超限 | 限流、告警或关闭连接 |
| `WS_INTERNAL_ERROR` | 未分类服务端错误 | 返回脱敏错误并记录 traceId |

业务错误码可以出现在业务事件的结果字段中，但不能用业务错误文本替代传输层错误码。错误消息不得包含 Ticket、Token、SQL、内部堆栈或敏感配置。

### 3.6 限制和配置

以下配置必须由服务端统一管理，并由运行配置提供明确值：

| 配置 | 约束 |
| --- | --- |
| `ticketTtl` | 短时有效；不得超过业务允许的握手窗口 |
| `maxTextFrameBytes` | 文本帧大小上限 |
| `maxBinaryFrameBytes` | 二进制帧大小上限 |
| `maxMessagesPerWindow` | 单连接消息频率上限 |
| `maxConnectionsPerUser` | 单用户并发连接上限 |
| `heartbeatInterval` / `idleTimeout` | 心跳和空闲超时 |
| `sendQueueLimit` | 慢消费者发送队列上限 |
| `allowedOrigins` | 生产环境 Origin 白名单 |

配置变更必须记录影响范围和回滚方式；前端不得通过参数绕过限制。

## 4. 业务逻辑设计

### 4.1 鉴权和资源授权

连接认证和业务资源授权分为两步：

1. Ticket 证明用户在申请时具有连接范围；
2. Handler 在加入房间、订阅和每个写入动作前重新校验当前成员关系、角色和资源权限。

连接建立后角色被撤销时，后续订阅和写入必须 fail-closed。读权限不能推导出写权限；持有连接不能替代业务 Guard。

### 4.2 房间和订阅

客户端连接后先声明订阅意图，服务端根据 Ticket 绑定范围校验资源。订阅成功后服务端返回 ACK；取消订阅、断开连接和权限撤销必须清理对应房间成员关系。

服务端广播前必须确认目标房间仍属于当前授权范围。禁止使用客户端传入的任意 `roomId`、`workspaceId` 或 `projectId` 作为可信授权依据。

### 4.3 消息处理顺序

文本业务事件按以下顺序处理：

1. 校验帧大小、JSON 结构和协议版本；
2. 根据 `requestId` 做幂等检查；
3. 校验订阅范围和写权限；
4. 调用业务 Service 执行状态校验和持久化；
5. 根据业务设计生成结果或副作用；
6. 向房间广播允许广播的结果；
7. 发送 ACK 或错误帧。

如果业务设计要求先广播后持久化，必须在对应业务详细设计中明确一致性窗口、失败补偿和重放策略；通用传输层不替业务选择该语义。

### 4.4 连接生命周期

服务端和客户端必须共同处理：

- 初次连接、Ticket 过期和握手拒绝；
- Ping/Pong、心跳超时和空闲关闭；
- 网络断开、指数退避重连和 Ticket 重新申请；
- 服务重启、多实例广播和房间恢复；
- 慢消费者、发送失败和队列清理；
- 权限撤销后的强制断开或后续操作拒绝。

重连不得重复执行未声明幂等策略的业务动作。客户端重连前不得复用已消费 Ticket。

### 4.5 广播和持久化边界

Handler 负责连接生命周期、帧分发和房间广播；业务 Service 负责资源校验、事务和持久化。跨实例广播使用框架分布式能力时，必须明确 Redis 可用性、消息顺序和失败降级。

WebSocket 文本写入操作的数据库事务边界、异步落库、重试和冲突处理由业务详细设计定义。无论采用同步还是异步持久化，都必须在广播前完成必要的权限校验，并保证错误不会泄露内部异常。

## 5. 前端设计

### 5.1 连接适配器

前端通过统一的实时连接适配器管理 Ticket 申请、WebSocket 创建、心跳、重连、消息解析和销毁。页面组件不直接拼接长期 Token，不直接操作房间成员关系，也不重复实现底层协议。

适配器对外提供：

- 连接状态和断开原因；
- Ticket 刷新和重新握手；
- 发送文本/二进制消息；
- 按 `requestId` 关联 ACK 和错误；
- 受控的业务事件分发。

### 5.2 页面使用规则

- 页面进入允许协作的资源范围后才申请 Ticket；
- 页面离开、文档切换或权限失效时主动关闭连接；
- 重连采用带抖动的退避策略，避免 Ticket 过期时集中重试；
- 连接失败、无权限、协议错误和业务错误分别展示；
- UI 不显示或记录 Ticket、完整 Payload 或内部 traceId；
- 评审、只读和编辑模式使用各自业务详细设计定义的事件，不在本适配器中硬编码业务语义。

### 5.3 兼容和降级

实时能力不可用时，页面按业务设计进入只读或 HTTP 降级模式；不得以重连循环掩盖权限错误。降级状态、恢复条件和用户提示必须由业务页面统一定义。

## 6. 实施说明

### 6.1 当前实现映射和差距

当前代码通过 migoo WebSocket Starter 的 `MiGooWebSocketHandler` 和 `WebSocketSessionManager` 管理连接，文档业务已有独立 Handler。该适配器的业务事件和持久化规则由对应业务详细设计维护。

| 能力 | 当前实现 | 目标状态 | 任务 |
| --- | --- | --- | --- |
| 连接端点 | `/ws/documents/{docId}` | 保留资源端点，凭证改为一次性 Ticket | DOC-005、SEC-005 |
| 握手凭证 | 迁移兼容的查询参数 Token | 短时、一次性、单资源 Ticket | SEC-005、SEC-013 |
| 身份认证 | Starter 握手认证 | Ticket 消费后重新校验身份和资源范围 | DOC-005 |
| 房间权限 | Handler 加入文档房间 | 通用订阅授权和房间隔离 | DOC-005 |
| 写权限 | 业务持久化处理器逐次校验 | 所有可写事件在广播/持久化前统一校验 | SEC-004 |
| Origin | 生产白名单需接入 | 握手阶段强制校验并审计 | SEC-005 |
| 错误帧 | 业务处理器使用局部字符串码 | 统一传输错误码，业务错误单独承载 | DOC-005 |
| 分布式广播 | 由框架能力承载 | 明确 Redis 依赖、顺序和降级 | DOC-005、OPS-004 |

### 6.2 依赖和实施顺序

1. 先确定 Ticket 服务的存储、TTL、原子消费和资源绑定；
2. 接入 Origin 白名单和日志脱敏；
3. 抽取通用连接/房间生命周期处理；
4. 将现有业务 Handler 迁移到统一消息信封和错误帧；
5. 为写权限、慢消费者、重连和多实例广播补齐测试；
6. 通过 Nginx/网关配置完成 WSS、Upgrade 和长连接超时验证。

### 6.3 验证清单

- [ ] Ticket 缺失、过期、重复消费和资源不匹配均拒绝握手
- [ ] Origin 非白名单请求拒绝且不进入业务房间
- [ ] 只读成员可按业务设计读取，但不能发送可写事件
- [ ] 权限撤销后现有连接的后续写入 fail-closed
- [ ] 文本/二进制帧大小、频率、版本和幂等校验可验证
- [ ] Ping/Pong、断线重连、服务重启和慢消费者行为可验证
- [ ] 多实例房间广播顺序和 Redis 故障降级可验证
- [ ] Ticket、Token、用户 ID、资源 ID 和完整 Payload 不进入普通日志
- [ ] 业务事件、Payload、持久化和冲突语义由业务详细设计覆盖
