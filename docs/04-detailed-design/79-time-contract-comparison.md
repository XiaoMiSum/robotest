# 软件测试平台——时间契约双方案比较

**文档版本**：V1.0
**日期**：2026-09-24
**状态**：起草中

---

## 1. 引言

### 1.1 编写目的

本文对时间字段的两种候选模型进行详细比较：

- 方案 A：当前兼容模型——UTC 语义的无时区 `LocalDateTime` + 数据库 `TIMESTAMP`；
- 方案 B：带时区模型——`Instant` / `OffsetDateTime` + PostgreSQL `TIMESTAMPTZ`。

本文对 API 时间和数据库存储模型进行分层处理：API 时间字段已确定统一输出带 `Z` 的 UTC；数据库类型和历史数据回填仍需按本文评估，不得把 API 格式决定误认为数据库迁移已经完成。

### 1.2 适用范围

适用于数据库时间字段、API 请求/响应、审计记录、报告、导入导出、异步任务、WebSocket/SSE 时间、前端解析和跨时区展示。

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| 无时区时间 | Java `LocalDateTime` 或数据库 `TIMESTAMP`；类型本身不携带时区/瞬时语义 |
| 带时区时间 | Java `Instant`、`OffsetDateTime` 或数据库 `TIMESTAMPTZ`；可确定唯一瞬时或保留偏移 |
| UTC | 协调世界时；系统统一存储和传输的基准时区 |
| 本地时间 | 用户或设备所在时区的时间，不应与 UTC 存储值混称 |

## 2. 数据设计

### 2.1 方案 A：当前兼容模型

#### 数据类型

| 层次 | 建议类型 | 说明 |
| --- | --- | --- |
| Java | `LocalDateTime` | 不携带 offset；应用约定所有值为 UTC |
| PostgreSQL | `TIMESTAMP WITHOUT TIME ZONE` | 不保存时区；写入前由应用统一转换 |
| JSON | ISO-8601 UTC 字符串 | API 统一输出带 `Z` 的 UTC；无时区值只能作为存储/历史兼容输入 |
| 前端 | 统一时间解析适配器 | 解析后按用户时区显示；不得直接把字符串当本地时间 |

#### 优点

- 与当前 Java 类型、Mapper、DTO 和已有数据脚本兼容；
- 迁移成本低，短期可继续使用现有索引和查询；
- 对只需要日期、月份或同一时区业务时间的场景实现简单。

#### 风险

- 类型本身不能防止 UTC 与本地时间混写；
- 跨时区转换、浏览器解析和历史数据回填容易产生隐性偏差；
- 夏令时、无 offset 时间和跨日边界需要应用层自行处理；
- `TIMESTAMP` 与 MySQL/其他数据库的时区行为需要额外约定。

### 2.2 方案 B：带时区模型

#### 数据类型

| 层次 | 建议类型 | 说明 |
| --- | --- | --- |
| Java 事件/审计时间 | `Instant` | 适合机器时间、排序和跨时区传输 |
| Java 本地业务时间 | `OffsetDateTime` | 需要保留原始 offset 时使用 |
| PostgreSQL | `TIMESTAMPTZ` | 存储规范化的瞬时语义；展示时由应用/数据库转换 |
| JSON | UTC `Instant` ISO-8601（含 `Z`） | 跨端契约稳定，前端按用户时区展示 |
| 前端 | `Date` + 统一时区适配器 | 解析、格式化和相对时间计算集中处理 |

#### 优点

- 类型层面携带唯一瞬时或 offset，减少 UTC/本地时间误用；
- 跨时区、夏令时和分布式服务的时间语义更清晰；
- 审计、事件排序和跨区域部署更容易保持一致。

#### 风险

- DTO、Entity、Mapper、Jackson 配置、前端解析和测试需要联动修改；
- 现有 `TIMESTAMP` 历史数据需要明确原始时区假设和回填策略；
- 日期型业务字段（如业务日期、月份）不能机械迁移为瞬时时间；
- PostgreSQL、MySQL 兼容环境和报表 SQL 需要验证行为差异。

### 2.3 数据分类

| 业务类别 | 方案 A | 方案 B | 备注 |
| --- | --- | --- | --- |
| 审计事件发生时间 | 可用，需统一 UTC 约定 | 推荐使用 `Instant` | 发生时间应可比较和排序 |
| 创建/更新时间 | 可用 | 推荐使用带时区类型 | 不能只依赖数据库默认值表达应用时区 |
| 业务日期、预约日期、月份 | `LocalDate` | `LocalDate` | 不应为了统一而改成时间戳 |
| 报告执行开始/结束 | 可用 | 推荐 | 需要计算持续时间和跨时区排序 |
| 用户展示时间 | 应用转换 | 应用转换 | 展示时区由用户/租户配置决定 |
| 定时任务 Cron | 业务时区需单独配置 | 业务时区需单独配置 | Cron 的业务时区不由 Java 时间类型自动决定 |

## 3. 接口详细设计

### 3.1 方案 A 的 JSON 形态（仅用于存储/历史兼容说明）

方案 A 的无时区字符串只用于说明当前 `LocalDateTime`/`TIMESTAMP` 存储兼容模型，不再作为事件时间 API 的输出格式：

```json
{
  "createdAt": "2026-09-24T12:00:00",
  "updatedAt": "2026-09-24T12:30:00"
}
```

当前 API 时间字段必须输出带 `Z` 的 UTC 字符串；无时区值只允许作为数据库存储或历史兼容输入，不得作为新 API 响应格式。

### 3.2 方案 B 的 JSON 形态

```json
{
  "createdAt": "2026-09-24T12:00:00Z",
  "updatedAt": "2026-09-24T12:30:00Z"
}
```

响应瞬时时间统一使用 UTC；既有 `LocalDateTime` 请求字段仍接收无时区墙钟值，由服务端持久化适配层完成一次转换，新设计的 `Instant`/`OffsetDateTime` 请求再要求显式 offset。

### 3.3 查询、排序和分页

两种方案都必须：

- 对时间范围参数定义闭区间/开区间语义；
- 明确默认排序和同一时刻的决胜键；
- 在游标分页中把时间与 ID 作为稳定锚点；
- 对非法时间、空值、时区缺失和夏令时重复时刻返回参数错误；
- 不把前端本地化字符串直接传给数据库。

## 4. 业务逻辑设计

### 4.1 当前兼容模型的业务约束

如果继续采用方案 A：

1. 所有服务端持久化值按 UTC 写入，代码和脚本必须一致；
2. Entity、DTO 和 JSON 适配层统一序列化规则；
3. 业务日期使用 `LocalDate`，不与 `LocalDateTime` 混用；
4. 定时任务、报告和审计的“业务时区”单独配置并记录；
5. 前后端必须通过统一解析器处理时间，不在页面中直接 `new Date(string)`；
6. 新接口评审必须检查时间字段的时区语义，即使类型名称不携带 offset。

### 4.2 带时区模型的业务约束

如果采用方案 B：

1. 所有事件时间在服务端以 UTC 瞬时保存；
2. 业务日期、用户展示时区和 Cron 业务时区分字段表达；
3. API 入口和出口统一 Instant 序列化，必要时保留 offset；
4. 数据库、ORM、缓存、消息和任务表的时间类型同步迁移；
5. 前端按用户时区显示，跨时区比较和相对时间由统一库处理；
6. 历史数据迁移前必须确认原始时间解释，不能仅执行类型 ALTER。

### 4.3 审计、报告和实时消息

- 审计时间属于事件发生时间，优先保证可排序、不可歧义；
- 报告开始/结束时间需要计算持续时间，不能只依赖字符串字典序；
- SSE/WebSocket 帧中的时间字段必须声明时区和版本；
- 异步任务的重试、过期和保留时间使用统一时间基准；
- 任何方案都必须在日志中避免输出不必要的精确用户时间。

## 5. 前端设计

### 5.1 解析层

前端建立统一时间适配器，至少提供：

- 解析 API 时间；
- 转换为 UTC 瞬时；
- 按用户时区格式化；
- 计算相对时间和持续时间；
- 处理空值、无效值和无时区字符串。

页面和业务组件不得自行复制不同的 `Date` 解析逻辑。解析失败时显示可理解的空态/错误态，不静默使用浏览器本地时区替代服务端值。

### 5.2 展示层

- 列表可按产品要求显示本地时间，并明确时区；
- 审计和跨区域协作按浏览器时区展示，必要时同时提供 UTC；
- 业务日期不显示时分秒，避免把日期误读为瞬时时间；
- 相对时间必须基于真实瞬时计算，不能用服务器时间字符串直接拼接。

### 5.3 兼容期

在迁移期间，前端解析器可以兼容旧无时区字符串和新 `Z` 字符串，但必须记录兼容期限、来源接口和异常监控；不能把兼容逻辑扩散到页面组件。

## 6. 实施说明

### 6.1 方案 A 的迁移成本

- 统一 DTO/JSON 适配和前端解析器；
- 审查所有 `LocalDateTime` 写入、默认值、查询范围和报表 SQL；
- 补充 UTC 约定、跨日、夏令时和历史数据测试；
- 保留现有数据库索引，通常无需类型迁移；
- 适合时间格式问题主要局限在应用层的短期阶段。

### 6.2 方案 B 的迁移成本

- 全量盘点 Entity、DTO、Mapper、TypeHandler、缓存键、消息 Payload 和导出文件；
- 设计 PostgreSQL `TIMESTAMP` → `TIMESTAMPTZ` 的历史数据回填和校验；
- 验证 MySQL 兼容环境、报表 SQL、排序和索引行为；
- 同步 Jackson、OpenAPI、前端类型和所有消费者；
- 为灰度期间的双读/双写或适配层制定回滚方案；
- 适合跨时区、审计、分布式部署和长期平台化目标。

### 6.3 验证矩阵

| 场景 | 方案 A 验证 | 方案 B 验证 |
| --- | --- | --- |
| UTC 写入后读取 | 确认无隐式本地时区转换 | 确认瞬时值不丢失 |
| 跨日查询 | 覆盖 UTC 日界和业务时区日界 | 覆盖 offset/用户时区日界 |
| 夏令时切换 | 验证重复/缺失本地小时的业务处理 | 验证 Instant 与 OffsetDateTime 转换 |
| 报告持续时间 | 验证同秒/跨秒计算 | 验证时区转换后的持续时间 |
| 审计排序/游标 | 验证时间加 ID 锚点 | 验证时间加 ID 锚点 |
| API 序列化 | 验证无 `Z` 字符串的统一解释 | 验证 `Z` 和 offset 输入输出 |
| 历史数据 | 验证现有值按 UTC 解释 | 验证回填前后值一致 |
| 前端展示 | 验证不误用浏览器时区 | 验证按用户时区展示 |

### 6.4 选择标准

最终选择应至少评估：

1. 业务是否需要跨时区协作或审计；
2. 当前部署和数据库兼容范围；
3. 历史数据原始时区是否可证明；
4. API 和前端类型迁移的可接受周期；
5. 报表、定时任务和消息系统的改造成本；
6. 团队对 `LocalDate`、UTC 和 offset 的统一能力。

## 7. 结论

API 响应时间契约已确定：时间字段统一使用带 `Z` 的 UTC ISO-8601，前端按浏览器时区展示。既有 `LocalDateTime` 请求仍由服务端持久化适配层完成一次本地到 UTC 转换；数据库存储模型和历史数据迁移仍不在本阶段自动执行。在迁移确认前：

- 新增设计必须注明采用的时间语义和时区；
- 既有 `LocalDateTime` 请求不得由前端预先转换为 `Z`，避免与框架层重复转换；
- 不得以“框架序列化默认行为”替代 API 响应契约；
- 不得只修改数据库类型而遗漏 API、前端、缓存和历史数据；
- 存储方案确认后更新本文、数据库规范、API 规范和相关详细设计。
