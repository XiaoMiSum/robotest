**文档版本**：V1.0
**日期**：2026-09-24
**状态**：已发布

## 1. 分支模型

> 分支模型保留 `master` 作为生产主分支，日常集成和功能分支按以下模型管理。

```text
master      ←──────────────────────────────
               ↑ PR
develop      ←──────────────┬──────────────
               ↑ PR          ↑ PR
feature/*    fix/*          release/*
hotfix/* ─────────────────────┘
```

| 分支 | 用途 | 来源 | 目标 |
| --- | --- | --- | --- |
| `master` | 生产就绪版本 | `develop` 或 hotfix | 发布 |
| `develop` | 日常集成 | `master` | `feature/*` / `fix/*` |
| `feature/*` | 新功能 | `develop` | `develop` |
| `fix/*` | 常规缺陷 | `develop` | `develop` |
| `release/*` | 发布准备 | `develop` | `master`、`develop` |
| `hotfix/*` | 生产紧急修复 | `master` | `master`、`develop` |

- 禁止直接向 `master` 和 `develop` 推送代码。
- 所有合并通过 PR 完成。
- `master` 和 `develop` 必须配置分支保护和必需检查。
- 发布和 hotfix 必须同步回 `develop`，避免修复丢失。

## 2. 提交规范

提交信息格式：

```text
<emoji> <type>(<scope>): <description>
```

### 2.1 类型

| Emoji | type | 用途 |
| --- | --- | --- |
| ✨ | `feat` | 新功能 |
| 🐛 | `fix` | Bug 修复 |
| ♻️ | `refactor` | 重构 |
| 💄 | `style` | 格式调整 |
| 📝 | `docs` | 文档 |
| ✅ | `test` | 测试 |
| 🔧 | `chore` | 构建、CI、依赖 |
| ⚡ | `perf` | 性能 |
| ⬆️ | `deps` | 依赖升级 |
| 🔒 | `security` | 安全 |

### 2.2 Scope

| Scope | 范围 |
| --- | --- |
| `domain/<scope>` | 按业务域或模块划分 |
| `backend` | 后端公共变更 |
| `frontend` | 前端公共变更 |
| `docs` | 文档 |
| `config` | 配置和构建 |
| `shared` | 跨模块公共变更 |

### 2.3 提交粒度

- 一个提交只完成一个逻辑单元。
- 不混合新功能、无关重构和格式化。
- 描述重点是做了什么和为什么做，不描述实现细节。
- 提交前必须完成相应验证；紧急 hotfix 也要完成最小回归。

## 3. Pull Request

### 3.1 PR 标题

PR 标题使用：

```text
[模块] 变更描述
```

例如：

```text
[api] 统一分页参数和 OpenAPI 契约
```

PR 标题和 Commit Message 是两个不同字段，不得混用。

### 3.2 PR 模板

```markdown
## 关联需求/缺陷

## 变更类型

- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档
- [ ] 安全
- [ ] 其他

## 变更内容

## 影响范围

- [ ] 前端
- [ ] 后端
- [ ] API/OpenAPI
- [ ] 数据库/迁移
- [ ] 部署/配置
- [ ] 安全

## 验证证据

- [ ] lint
- [ ] typecheck
- [ ] 单元测试
- [ ] 契约检查
- [ ] 手动测试
- [ ] 构建/部署验证

## 风险与回滚

## 规范和文档同步
```

### 3.3 审查要求

审查者必须确认：

- 需求、设计和实现一致；
- API、数据库和权限影响已说明；
- 必要测试已补充；
- 文档和 AGENTS 引用已同步；
- 敏感信息、日志和配置没有泄露；
- 回滚和迁移方案可执行；
- PR 未混入无关变更。

## 4. CI 必需检查

以下检查应在分支保护中配置为必需：

- 前端 lint；
- 前端 typecheck；
- 前端单元测试；
- 后端编译和测试；
- OpenAPI 契约一致性；
- C1 / C4 / C5 / C11 等适用规则检查（C4 按业务详细设计执行）；
- 依赖漏洞和敏感信息扫描。

`07-quality.md` 负责定义门禁内容，本文只负责流程和合并策略。

## 5. 发布和回滚

- 发布分支必须明确版本号、变更范围、数据库迁移和配置变更。
- 发布前必须完成测试环境验证和生产配置检查。
- 数据库迁移必须先备份并提供恢复方案。
- 应用回滚不能依赖未验证的数据库逆向迁移。
- 发布后检查健康状态、核心接口、认证、核心资源访问和实时连接。
- 紧急修复必须记录影响、验证结果和后续补发计划。

## 6. 文档变更

- 规范、设计和交互文档变更必须与实现同步。
- 文档修改遵循 `docs/AGENTS.md`。
- 规则变更必须说明适用范围、检查方式、迁移影响和验证证据。
- 不得通过修改文档掩盖未实现的代码行为。

## 7. 例外

- 纯拼写、错别字和不改变含义的格式修复可以走轻量流程，但仍需检查链接和渲染。
- 紧急 hotfix 可以先合并后补齐非阻塞材料，但安全和数据风险项不得省略。
- 任何流程例外必须记录原因、批准人和补救时间。
