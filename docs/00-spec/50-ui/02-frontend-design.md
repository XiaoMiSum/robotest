# 前端通用设计规范

**文档版本**：V1.0
**日期**：2026-09-24
**状态**：已发布

---

## 1. 引言

### 1.1 编写目的

本规范定义前端页面和组件的通用视觉、布局、交互状态、响应式和可访问性要求，目标是在不同业务模块之间保持一致、可复用和可维护的体验。

本规范聚焦通用设计原则和验收方法；具体视觉令牌、产品视觉语言和页面布局由设计系统或交互设计文档提供。

### 1.2 适用范围

适用于前端页面、组件、布局容器、表单、列表、弹层、状态提示和交互控件。技术实现可以采用不同的组件库和样式方案，但必须满足本规范的行为和质量要求。

### 1.3 与其他规范的关系

- 组件分层、依赖方向和 TypeScript 约束见 `docs/00-spec/10-engineering/01-frontend.md`。
- 页面拆分、状态归属和小组件开发见 `docs/00-spec/50-ui/03-page-development.md`。
- 滚动容器和滚动条行为见 `docs/00-spec/50-ui/01-scroll-container.md`。
- 业务页面结构、文案和交互流程由对应的需求、设计和交互文档定义。
- 设计令牌的具体值由设计系统事实源提供，本规范只规定令牌的类别和使用方式。

### 1.4 定义与缩写

| 术语 | 定义 |
| --- | --- |
| 设计令牌 | 用于描述颜色、间距、排版、圆角、阴影、层级和动效的可复用设计变量。 |
| 视觉层级 | 用户感知信息重要程度、空间关系和操作优先级的整体结构。 |
| 语义状态 | 表示正常、加载、警告、错误、禁用等含义的状态，不等同于某个具体颜色。 |
| 内容区域 | 承载页面主要信息或交互的布局区域。 |
| 设计一致性 | 相同语义在不同页面使用相同或等价的视觉和交互表达。 |

## 2. 总体设计原则

### 2.1 UI-DS-01：保持语义一致

相同含义的信息、控件和状态必须使用一致的视觉表达、名称和交互方式。颜色、图标、形状、文案和动效应共同表达语义，不能只依赖单一通道。

### 2.2 UI-DS-02：先建立层级，再安排细节

页面应先明确主标题、主要内容、主要操作和次要信息的层级，再处理间距、边框和装饰。装饰元素不得削弱主要任务的识别和操作。

### 2.3 UI-DS-03：优先使用设计令牌

颜色、间距、字体、圆角、阴影、层级和动效优先引用设计令牌。不得在组件中随意硬编码视觉值；确需新增令牌时，必须说明语义、适用范围和默认值。

### 2.4 UI-DS-04：状态必须完整

每个数据组件和交互组件都必须考虑正常、加载、空数据、错误、禁用、提交中、权限不足和成功反馈等适用状态。组件不得只实现成功路径。

### 2.5 UI-DS-05：反馈及时且可解释

用户操作必须得到及时反馈。提交、加载、删除、排序、保存和失败重试等操作应说明当前状态、是否可以继续以及下一步如何处理。

### 2.6 UI-DS-06：布局具备响应式能力

布局应从内容关系出发设计，在窄屏、宽屏、长文本、长时间数据和无障碍放大场景下保持可读、可操作和稳定。不得仅通过缩小字号或压缩间距适配窄屏。

### 2.7 UI-DS-07：默认支持键盘和辅助技术

可操作控件必须具备可识别的名称、可见焦点、合理 Tab 顺序和键盘行为。不得用鼠标专属交互替代标准控件能够完成的操作。

### 2.8 UI-DS-08：视觉变化服务于任务

动效、阴影、渐变、动画和装饰性图形必须服务于状态变化、空间关系或注意力引导，并遵守减少动效偏好。不得为了视觉效果增加影响阅读或操作的噪声。

## 3. 视觉与布局

### 3.1 信息层级

页面应根据任务重要性组织内容，通常包括以下层级：

1. 页面或区域标题：说明当前上下文和主要任务；
2. 描述与状态摘要：帮助用户判断当前数据或操作结果；
3. 主要操作：完成页面最核心的任务；
4. 筛选、搜索和工具栏：支持用户定位和控制内容；
5. 主要内容：承载数据、表单、媒体或交互区域；
6. 辅助信息和次要操作：提供补充上下文，不应抢占主要视觉焦点。

层级应通过空间、字号、字重、对齐、容器和对比度共同表达，不得只依靠颜色深浅。

### 3.2 页面布局

- 页面应使用清晰的容器层级区分壳层、页面头部、工具栏、内容区和辅助区域。
- 同一层级的区域应保持对齐方式和间距节奏一致。
- 横向布局应明确最小宽度、换行和伸缩规则；纵向布局应明确内容增长、收缩和滚动边界。
- 不得使用大量无意义嵌套容器弥补布局问题；容器数量应服务于语义和布局职责。
- 页面内容超出视口时，应由 `docs/00-spec/50-ui/01-scroll-container.md` 规定的唯一滚动拥有者负责滚动。

结构示意：

```text
┌─────────────────────────────────────────────┐
│ 页面标题 / 页面状态 / 主要操作                  │
├─────────────────────────────────────────────┤
│ 筛选、搜索、视图切换等工具栏                    │
├─────────────────────────────────────────────┤
│                                             │
│                 主要内容区域                  │
│                                             │
├─────────────────────────────────────────────┤
│ 分页、统计或其他辅助区域                       │
└─────────────────────────────────────────────┘
```

### 3.3 间距与密度

- 页面、区域、控件和文字之间应使用统一的空间尺度。
- 相关内容使用较紧凑的间距，区分不同区域时使用更明显的间距或容器边界。
- 不得通过任意 `margin` 叠加制造层级；优先使用统一的布局属性和令牌。
- 同一页面不得同时混用多套未经说明的间距尺度。
- 触摸目标、图标按钮和紧凑控件必须保留足够的可操作区域。

### 3.4 排版

- 标题、说明、正文、辅助文字和表格文字应形成稳定的字号与字重层级。
- 同一层级的内容保持字体、行高、字间距和对齐方式一致。
- 长文本必须支持换行、截断提示或展开查看，不能因固定宽度造成内容截断或布局溢出。
- 数字、代码、标识符和时间等需要精确比较的内容应使用适合对齐和识别的排版方式。

### 3.5 颜色与语义状态

颜色必须通过语义令牌使用，不得把某个具体色值直接当作业务含义。至少应区分以下语义：

| 语义 | 表达内容 | 设计要求 |
| --- | --- | --- |
| 默认 | 正常信息和可操作控件 | 保持足够的文字和背景对比度 |
| 强调 | 主要操作、选中态或焦点 | 只用于需要突出注意力的内容 |
| 成功 | 操作完成或状态正常 | 同时配合文案、图标或形状 |
| 警告 | 需要注意但可以继续 | 不得只依赖颜色表达 |
| 错误 | 操作失败或数据异常 | 提供可理解的错误信息和恢复动作 |
| 禁用 | 当前不可操作 | 保留可读性并说明不可操作原因（如适用） |
| 信息 | 中性说明或辅助状态 | 不得与成功状态混淆 |

状态设计应使用“颜色 + 图标/形状 + 文案”的组合，具体组合由设计系统统一维护。

### 3.6 边框、圆角、阴影与层级

- 边框用于表达边界、关系或状态，不用于弥补布局不清晰。
- 圆角应保持同一视觉语言，避免同级容器使用不一致的圆角。
- 阴影用于表达浮层、悬浮或层级关系，不得无差别地施加到所有容器。
- 弹层、抽屉、对话框和固定工具栏必须明确其层级和关闭方式。
- 不得使用视觉效果掩盖内容溢出、错误状态或不可操作状态。

### 3.7 图标与插图

- 图标必须服务于可识别的操作或状态，并提供可访问名称或文本说明。
- 相同图标不得在不同页面表达不同动作；同一动作也不得无理由使用多个图标。
- 装饰性图标应标记为装饰，传达信息的图标必须有等价文本。
- 插图应服务于理解、引导或反馈，不应遮挡主要内容或降低文字可读性。

## 4. 组件设计

### 4.1 组件结构

组件应具有清晰的结构和边界：

- 容器负责布局和区域边界；
- 内容负责呈现数据和文本；
- 操作负责触发事件；
- 状态负责表达加载、错误、禁用和反馈；
- 扩展内容通过插槽或组合方式提供。

组件应优先通过组合复用，而不是通过不断增加布尔属性覆盖大量不同形态。若一个组件需要大量互斥配置，应评估是否应拆分为多个语义更明确的组件。

### 4.2 组件状态

所有交互组件至少应定义以下适用状态：

| 状态 | 必须表达的内容 |
| --- | --- |
| 默认 | 可用状态下的内容和操作 |
| Hover | 鼠标或指针悬停时的辅助反馈 |
| Focus | 键盘焦点和当前操作对象 |
| Active/Pressed | 操作正在进行或被按下 |
| Selected | 当前选中、激活或打开状态 |
| Disabled | 不可用时的外观和必要原因 |
| Loading | 操作或数据正在处理 |
| Error | 失败原因摘要和恢复方向 |
| Read-only | 可阅读但不可编辑的边界 |

不适用的状态可以省略，但必须在组件设计或测试范围中明确说明。

### 4.3 交互反馈

- 点击、提交、切换、拖拽、展开、收起和删除等操作必须有可观察反馈。
- 异步操作应防止重复提交，并明确进行中、成功和失败状态。
- 破坏性操作应提供确认、撤销或其他等效保护机制，具体方式按风险决定。
- 错误提示应说明用户可以采取的动作，不应只显示内部错误文本。
- 成功反馈不应阻塞用户继续浏览，除非业务确实要求等待确认。

### 4.4 受控与非受控

组件应明确数据所有权：

- 受控组件由父级或页面持有值，并通过 Props/事件更新；
- 非受控组件在自身管理内部临时状态，但必须提供清理和重置机制；
- 同一交互不得同时存在多个互相覆盖的值来源；
- 双向绑定必须定义清晰的更新事件和值类型。

### 4.5 组合与扩展

- 优先使用默认插槽表达内容扩展，使用命名插槽表达结构扩展。
- 组件不应依赖外部未声明的 DOM 结构或 CSS 选择器。
- 组件对外暴露的 Props、Emits 和 Slots 应有稳定名称和明确语义。
- 需要高度定制的场景可以提供低层构建块，但不得破坏基础组件的可访问性和状态一致性。

## 5. 响应式与可访问性

### 5.1 响应式布局

- 断点应由内容何时无法舒适阅读或操作决定，而不是机械套用设备名称。
- 窄屏下应优先保留主要任务和关键操作，次要信息可以折叠、换行或延后展示。
- 固定格式工具应提供横向滚动、换行或响应式替代方案，不能静默裁剪关键内容。
- 触摸设备上的点击目标、间距和操作顺序必须适合手指操作。
- 不得依赖 hover 才能发现主要操作或关键信息。

### 5.2 可访问性

- 使用语义化 HTML 元素表达页面结构、标题、导航、表单和列表。
- 每个输入控件必须有可关联的标签、说明或可访问名称。
- 错误信息应与对应控件建立关联，并在需要时通过 `aria-describedby` 等方式提供描述。
- 弹层打开后应管理焦点，关闭后应尽量恢复到触发控件。
- 不得移除默认焦点样式而没有等效的焦点指示。
- 状态变化应使用适当的状态通知机制，避免屏幕阅读器无法感知。
- 触控、鼠标和键盘操作应完成相同的核心任务。

### 5.3 减少动效

遵循用户的减少动效偏好。动效应可中断、不可阻塞操作，并避免快速闪烁或大幅位移。状态反馈优先使用静态样式和文本表达。

## 6. 设计令牌与实现

### 6.1 令牌分类

设计系统至少应区分以下类别：

| 类别 | 内容 |
| --- | --- |
| 色彩 | 背景、文字、边框、品牌、语义状态和交互状态 |
| 排版 | 字体、字号、字重、行高和字间距 |
| 间距 | 页面、区域、控件、图标和文本之间的空间尺度 |
| 形状 | 圆角、边框宽度和控件尺寸 |
| 层级 | 阴影、层级、遮罩和浮层关系 |
| 动效 | 时长、缓动和过渡用途 |
| 布局 | 容器宽度、列数、断点和内容最大宽度（如适用） |

### 6.2 令牌使用

- 组件只能依赖已登记的令牌或组件级语义变量。
- 新令牌必须有明确语义，不能以具体页面或组件名称命名。
- 不得为了复用少量样式而创建语义模糊的全局变量。
- 组件库覆盖样式必须限定在组件根节点或明确的局部范围内。
- 主题切换、密度变化和响应式布局不应破坏令牌语义。

### 6.3 设计实现边界

具体色值、字体、间距数值、组件库覆盖和页面布局由设计系统及交互设计决定。本规范只要求这些实现具备统一语义、作用域边界和可维护的令牌来源。

## 7. 设计验收清单

| 编号 | 检查项 | 通过标准 |
| --- | --- | --- |
| UI-DS-01 | 语义一致 | 相同语义使用一致的文案、图标、颜色和交互方式。 |
| UI-DS-02 | 信息层级 | 主要任务、状态和操作入口清晰可辨。 |
| UI-DS-03 | 设计令牌 | 视觉值来自令牌，没有无理由的硬编码。 |
| UI-DS-04 | 状态完整 | 加载、空态、错误、禁用、提交中和成功状态适用且完整。 |
| UI-DS-05 | 反馈明确 | 用户操作有及时、可解释、可恢复的反馈。 |
| UI-DS-06 | 响应式 | 窄屏、宽屏、长文本和长内容下仍可读可操作。 |
| UI-DS-07 | 可访问性 | 键盘、焦点、语义结构和辅助技术可完成核心任务。 |
| UI-DS-08 | 动效克制 | 动效服务于任务并支持减少动效偏好。 |
