# 实时通信协议规范

**文档版本**：V1.0
**日期**：2026-09-24
**状态**：已发布

---

## 1. 适用范围

本规范定义平台通用 WebSocket API 的连接、鉴权、房间/主题、帧格式、错误、生命周期、安全和可观测性要求。

本规范不定义任何业务领域的数据模型、事件语义、协作算法或持久化规则。具体业务事件、Payload 字段和业务权限由对应的详细设计文档定义。

## 2. 连接和鉴权

### 2.1 鉴权方式

WebSocket 握手必须完成身份认证。推荐使用短时、一次性的连接 Ticket：

```text
HTTP API → 申请 ticket
WebSocket handshake → 提交 ticket
```

Ticket 必须：

- 绑定用户身份；
- 绑定允许访问的连接范围；
- 短时有效；
- 使用后失效或达到一次性消费条件；
- 不写入普通访问日志；
- 不替代业务资源权限校验。

如果客户端或网关只能通过查询参数传递凭证，必须：

- 使用短时凭证；
- 对代理、网关和监控日志脱敏；
- 限制来源 Origin；
- 制定凭证迁移和下线计划。

### 2.2 连接建立流程

服务端必须按以下顺序处理：

1. 校验连接凭证；
2. 校验用户身份和连接范围；
3. 校验 Origin（如配置了白名单）；
4. 建立连接并分配 session ID；
5. 记录连接元数据和审计事件；
6. 允许客户端订阅允许的房间或主题。

握手未通过时，服务端应拒绝连接或返回稳定的协议错误，不得先建立业务房间再异步补鉴权。

## 3. 房间和主题

### 3.1 房间/主题模型

- 连接可以订阅一个或多个允许的房间/主题。
- 房间/主题的创建、删除和成员资格由服务端控制。
- 客户端不得通过发送任意 roomId 绕过服务端授权。
- 同一用户是否允许多连接、重连复用和多标签页需要明确策略。

### 3.2 权限

- 连接认证只证明身份，不代表所有业务操作均有权限。
- 订阅、发布、接收和写入操作分别进行授权判断。
- 权限在连接存续期间被撤销时，后续操作必须 fail-closed。
- 业务 Handler 不得仅依赖前端连接状态判断权限。

## 4. 帧类型

本规范定义传输层帧，不定义业务事件类型。

| 帧类型 | 用途 | 约束 |
| --- | --- | --- |
| 文本 JSON 帧 | 控制、事件和业务消息 | 必须符合统一信封格式 |
| 二进制帧 | 高频、批量或二进制数据 | 必须定义最大大小、编码和权限 |
| Ping/Pong | 连接保活 | 必须由传输层或框架统一处理 |
| 错误帧 | 鉴权、协议、权限和传输错误 | 使用稳定协议错误码 |

二进制帧的具体格式、编码方式和业务含义由业务设计或独立协议定义。

## 5. 文本消息信封

推荐使用以下通用 JSON 信封：

```json
{
  "type": "event",
  "requestId": "request-id",
  "version": 1,
  "payload": {}
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 是 | 消息类型或动作类型 |
| `requestId` | 建议 | 请求追踪、幂等和日志关联 |
| `version` | 是 | 协议或消息版本 |
| `payload` | 按类型 | 业务数据，由详细设计定义 |

### 5.1 控制消息

可以定义以下传输控制类型：

- `subscribe`
- `unsubscribe`
- `ack`
- `ping`
- `pong`
- `error`

控制消息不得承载未声明的业务副作用。业务动作应使用独立的业务事件类型，并由业务设计明确权限和幂等规则。

### 5.2 业务事件

业务事件的 `type`、Payload 字段、顺序、版本和重放策略必须由对应详细设计定义。本规范只要求：

- 类型命名稳定；
- 字段有版本策略；
- Payload 有大小和类型校验；
- 事件有明确的请求 ID 或幂等策略；
- 业务错误与传输错误可区分。

## 6. 确认、错误和幂等

### 6.1 确认

需要确认的控制或业务操作必须支持：

- requestId；
- 成功或失败结果；
- 处理耗时或状态；
- 重复请求处理结果。

异步事件是否需要逐条 ACK，由业务设计决定，但必须在协议中明确。

### 6.2 错误帧

```json
{
  "type": "error",
  "requestId": "request-id",
  "code": "WS_PERMISSION_DENIED",
  "message": "无权执行该操作",
  "version": 1
}
```

传输层错误码至少区分：

- `WS_AUTH_FAILED`
- `WS_PERMISSION_DENIED`
- `WS_PROTOCOL_INVALID`
- `WS_MESSAGE_TOO_LARGE`
- `WS_RATE_LIMITED`
- `WS_INTERNAL_ERROR`

业务错误码可以在 Payload 中返回，但不得用业务错误文本代替稳定的传输层错误码。

### 6.3 幂等和重放

- 连接重试不得导致未声明的业务动作重复执行。
- 需要幂等的业务事件必须定义幂等键和重复响应。
- 事件重放必须声明顺序保证、版本兼容和去重策略。

## 7. 生命周期和可靠性

必须定义并测试：

- 初次连接和握手失败；
- Ping/Pong 和心跳超时；
- 断线重连；
- 凭证过期；
- 权限撤销；
- 订阅恢复；
- 网络异常和发送失败；
- 服务重启和多实例广播；
- 慢消费者和发送背压；
- 消息大小和速率限制。

客户端不得通过未登记的 JavaScript 滚动同步、手写底层协议或私有连接状态替代标准生命周期管理。

## 8. 安全要求

- 生产环境使用 WSS。
- Origin 使用明确白名单，禁止默认 `*`。
- 连接凭证、用户 ID 和业务资源 ID 不得写入普通日志。
- 每个订阅和发布操作都进行服务端授权。
- 消息大小、频率、连接数和单用户连接数有限制。
- 服务端返回错误不得泄露 Token、SQL、内部堆栈或敏感配置。
- 关键连接、订阅、取消订阅和权限失败事件进入安全审计。

## 9. 可观测性

服务端应记录：

- connectionId；
- userId（如适用，已脱敏）；
- 房间/主题；
- 协议版本；
- 连接、断开、订阅和权限失败原因；
- 消息数量、字节数和延迟；
- 重连次数和失败原因。

日志和指标必须避免记录完整 Payload 中的敏感字段。

## 10. 审查清单

- [ ] 连接鉴权和资源授权已分别实现
- [ ] 短时 Ticket 或凭证脱敏方案已配置
- [ ] Origin 白名单已配置
- [ ] 文本 JSON 信封和版本策略已定义
- [ ] 二进制帧的大小、编码和权限已定义
- [ ] ACK、错误、幂等和重连策略已定义
- [ ] 慢消费者、限流和背压策略已测试
- [ ] 日志、审计和监控字段已脱敏
- [ ] 业务事件和 Payload 已由对应详细设计定义
