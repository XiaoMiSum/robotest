# 软件测试平台——追溯矩阵

**文档版本**：V2.0  
**日期**：2026-10-17  
**状态**：起草中

---

## 1. 引言

### 1.1 编写目的

定义追溯矩阵的业务需求：以需求为起点，由 AI 执行全链路分析，把系统测试的全过程——测试设计、测试执行、缺陷修复与回验——连成可随时查看的只读链路，支撑发布前的覆盖判断与需求变更后的影响识别。本文为全量重写版本，上一版本全文由 Git 历史承载。

### 1.2 范围与边界

**覆盖**：全链路分析（AI 执行）、链路查看与反查、覆盖结论与缺口、变更影响标注。

**不覆盖（各归其主，追溯只读取、不复制）**：

- 模块 ▸ 脑图文档 ▸ 测试用例的组织结构——测试用例管理；
- 评审与测试计划的组织、采纳与快照——评审 / 计划管理；
- 执行结果的产生与维护——测试计划执行；
- 缺陷的生命周期与关联用例的编辑——缺陷管理；
- 页面与视图形态——交互设计。

**明确不做**：追溯矩阵**不提供任何写操作**——没有挂载、改挂、断开，没有覆盖复核，没有影响处置。人工在本能力内只有两个动作：**触发分析**与**阅读结果**。

### 1.3 定义与缩写

| 术语 | 定义 |
| ---- | ---- |
| 追溯矩阵 | 以需求为起点、由 AI 全链路分析贯通测试资产、评审与计划、执行结果与缺陷的平台级业务能力 |
| 全链路分析 | 由人工在需求管理页触发、AI 后台执行的分析动作：沿需求构建链路、判定资产与缺陷归属、给出覆盖结论与缺口，变更后重新分析给出受影响标注 |
| 全链路 | 需求 → 测试设计 → 测试执行 → 缺陷修复与回验的完整路径 |
| 来源关系 | 需求与其下游对象（模块、脑图文档、测试用例、缺陷）之间的归属对应；由分析建立（仅 AI），只读 |
| 归属判定 | 分析内部环节：判断未归属的用例与缺陷属于哪条需求并建立来源关系；判定不明确的保持未归属并给出建议 |
| 覆盖结论 | 分析按需求给出的测试充分性判定 |
| 缺口 | 链上某一环未补齐的情形，由分析标注在对应节点上 |
| 受影响标注 | 需求变更后重新分析时，对下游可能失效内容的只读标注 |
| 待分析 | 尚未执行过分析、或 AI 未启用时覆盖结论的状态 |

## 2. 总体描述

### 2.1 业务定位

系统测试的价值闭环是「业务需求 → 测试设计 → 测试执行 → 缺陷修复 → 回验需求」。追溯矩阵让这条闭环可查询、可度量，回答两个方向的问题：

- **正向（需求视角）**：这条需求测到什么程度——拆出了哪些测试设计、执行结果如何、遗留哪些缺陷、闭环没有；
- **反向（节点视角）**：这个用例、这条缺陷针对哪条需求——已归属的给出全链路，未归属的如实标注。

**能力以 AI 全链路分析为发动机**：链路、归属、覆盖、缺口、受影响标注全部是分析的产出；未执行过分析的需求，上述内容均不可得（显示待分析）。

### 2.2 典型使用场景

**发布前的覆盖检查**：临近发版，测试负责人在需求页对「登录验证码」触发全链路分析（或此前已执行过）。打开这条需求，沿链看到拆出的模块与脑图文档、每条用例是否经过评审、进了哪些计划、执行通过与失败各几条、失败的提没提缺陷、缺陷修没修完复验没有；链上哪一环没通，缺口标注在那一环的节点上。半分钟内能回答「敢不敢放行」。

**资产与缺陷的归属**：分析执行时，AI 顺带判定全项目未归属的用例与缺陷——能明确判断的自动挂到对应需求（标注 AI 建立），判不准的保持未归属并在相关需求的结果中标注建议归属（只读提示）。使用者不点任何按钮；发现归属不对时，唯一的途径是重新触发分析。

**变更后的影响识别**：需求内容变更后，人工重新触发分析；结果中标注下游可能失效的内容——基于旧版本写的用例、评审与计划快照落后于当前版本的环节、需要重新复验的缺陷——连同理由（只读）。实际的重新生成、重新评审发生在各业务入口，追溯不跟踪处理状态。

### 2.3 业务价值

- **资产与缺陷有归属**：任一对象可回答「针对哪条需求」，未归属的由 AI 判定归位；
- **测到什么程度有基准**：覆盖以需求为粒度、以链的通达程度与执行结果为据，结论可下钻核验；
- **变更不靠记忆**：变更后重新分析，受影响的下游连同理由自动列出；
- **断点不被掩盖**：链在哪一环断了，缺口就标在哪一环；
- **结论不可篡改**：分析产出只读，历次分析记录保留，谁在何时触发了哪次分析可还原。

### 2.4 验收口径

- **发布前**：任选一条已执行过分析的需求，可一次说清其全部测试支撑与当前状态；
- **任一时点**：任选一个用例或缺陷，可反查其来源需求与全链路；未归属的如实标注未归属（含 AI 建议归属）；
- **需求变更**：重新触发分析后，受影响下游清单完整、附理由，不依赖人工记忆；
- **审计复盘**：历次分析的触发人、时间、状态与结论可完整还原。

### 2.5 与相邻业务域的关系

- **需求管理**：需求条目是追溯的起点与度量粒度，需求列表承载覆盖状态的展示，触发入口在需求管理页；
- **功能测试**：组织结构、评审与计划采纳、执行结果的数据拥有者，追溯只读取；
- **缺陷管理**：缺陷生命周期与关联用例的拥有者，追溯沿归属关系建立回验、沿关联用例作补充回溯；
- **AI 能力**：全链路分析的唯一执行者；AI 不可用时本能力的分析不可执行，既有分析结果仍可查看。

## 3. 功能需求

### 3.1 全链路分析（US-TR-001）

**功能描述**：由人工在需求管理页触发、AI 后台执行的分析动作，产出链路、归属、覆盖、缺口与受影响标注；产出只读。

**功能点**：

- **触发**：仅人工在需求管理页触发（首次分析与重新分析同一入口）；无自动触发，不提供其他触发渠道。
- **执行**：AI 后台异步执行；执行期间**显示上次分析结果并标注「分析中」**，不空屏；执行失败可重新触发。
- **分析内容**：沿需求构建链路（模块、脑图文档、用例 → 评审与计划及采纳时点版本 → 执行结果 → 缺陷及回验状态）；判定未归属对象的归属并建立来源关系；给出覆盖结论与缺口；需求内容较上次分析已变更的，给出受影响标注。
- **归属判定**：能明确判断的自动归属并标注「AI 建立」；判不准的保持未归属，在相关需求的结果中标注建议归属（只读）。
- **结果只读**：分析产出不可编辑、不可修正、不可处置；人工唯一影响分析的方式是**重新触发**。
- **时效标注**：需求或下游内容较上次分析发生变更后，结果标注「已过时，建议重新分析」。

**业务规则**：

- 分析以需求为单位执行；已归档需求不作为分析输入，其历史结果保留可查。
- 未执行过分析、执行失败或 AI 未启用时，覆盖显示「待分析」，链路与缺口区为空态引导。
- 同一需求同时只进行一次分析；执行中重复触发不受理。

### 3.2 链路查看与反查（US-TR-002）

**功能描述**：读取全链路分析结果，支持由需求正向展开链路、由已归属对象反向反查。

**功能点**：

- **正向展开**：需求 → 拆出的模块、脑图文档与测试用例 → 所参与的评审与计划（含采纳时点的内容版本）→ 执行结果（通过 / 失败 / 阻塞 / 未执行）→ 关联缺陷及其回验状态，逐层可点开。
- **缺陷闭环口径**：链上缺陷「已修复且回验通过」为闭环；已修复未回验显示为未闭环。
- **反向反查**：任选一个已归属的用例或缺陷，反查其来源需求与全链路；未归属的如实标注未归属及其 AI 建议归属。
- **断点就地标注**：链上哪一环没通——用例未进评审、未进计划或未执行、执行失败未关联缺陷——标注在对应节点上。
- **版本锚定**：评审与计划引用采纳时点的用例内容；用例后续修改不改变既有采纳事实，链上可识别当时版本与当前版本的差异。
- **结构变动不丢归属**：资产在模块树中移动、重组、改名，其来源关系不受影响。

**业务规则**：

- 追溯只读取各业务域自有数据（组织、采纳、执行、缺陷关联），不产生副本；来源关系是追溯的唯一登记事实，由分析建立。
- 结果的查看范围限定在当前项目与工作空间内。

### 3.3 覆盖结论与缺口（US-TR-003）

**功能描述**：读取分析给出的覆盖结论与缺口标注；二者只读、随分析刷新。

**功能点**：

- **结论四档**：**未覆盖**（该需求没有测试用例）、**部分覆盖**（有用例但执行与回证未走完）、**充分覆盖**（链路走完、执行完成且无未闭环缺陷）、**待分析**（未执行过分析或 AI 未启用）；待分析不计入覆盖与未覆盖统计。
- **依据可核验**：结论可逐层下钻，展示得出结论所依据的用例、执行结果与缺陷；「存在来源关系」不等同于已覆盖。
- **缺口标注**：缺口随分析标注在链上节点——无下游用例、用例未进评审、未进计划 / 未执行、执行失败未关联缺陷、缺陷已修复未回验——每项附指向对应业务入口的提示（只读引导，追溯不代处理）。
- **对外展示**：覆盖结论是需求的属性，需求列表直接展示，作为全项目扫描入口；具体呈现形态由交互设计定义。

**业务规则**：

- 覆盖结论与缺口以最近一次成功分析为准；重新触发分析后整体刷新。
- 二者均为分析产出：只读、不可复核、不可人工调整。

### 3.4 变更影响标注（US-TR-004）

**功能描述**：需求变更后由人工重新触发分析，结果中标注下游可能失效的内容与理由。

**功能点**：

- **触发**：无独立触发渠道——需求变更后的受影响识别统一经「重新触发分析」完成。
- **标注内容**：沿链标注可能失效的下游——基于旧需求版本编写的用例、采纳快照落后于当前用例版本的评审与计划、需重新回验的缺陷——每项附理由（只读）。
- **边界**：标注仅是提示；重新生成、重新评审、复验等动作发生在各业务入口，由相应业务自行完成，追溯不跟踪处理状态、不记录处置结果。

**业务规则**：

- 受影响标注随本次分析产出、随下次分析刷新；不持久保留历次标注的处理轨迹。
- 标注基于分析时点的数据快照，标注本身不改动任何下游内容。

## 4. 非功能需求

- **只读性**：分析产出的全部内容不可编辑、不可修正、不可处置；本能力内的人工动作只有触发分析与阅读结果。
- **异步语义**：分析执行期显示上次结果并标注进行中；失败可重跑；同一需求同时至多一次分析。
- **可回溯性**：支持需求侧全链路展开与已归属对象的双向反查；断点必须可见，不得静默省略。
- **历史完整性**：历次分析记录（触发人、时间、状态、结论）保留可查；起链对象归档后历史结果保留。
- **隔离与权限**：追溯数据限定在所属项目与工作空间内；触发分析需相应权限，查看遵循既有数据隔离约定。
- **降级**：AI 不可用时分析不可执行，覆盖显示待分析、链路为空态引导；既有分析结果仍可查看。

## 5. 数据需求

**功能描述**：定义追溯矩阵涉及的数据实体及其关系（实体级，不含表结构）。

| 实体 | 性质 | 职责 |
| ---- | ---- | ---- |
| 全链路分析记录 | 追溯自有 | 需求、触发人、触发时间、状态（执行中 / 完成 / 失败）、基于的需求版本、完成时间与结论 |
| 来源关系 | 分析产出，只读 | 需求与下游对象（模块 / 脑图文档 / 测试用例 / 缺陷）的归属对应，含建立时机与归属判定建议 |
| 分析结论 | 分析产出，只读 | 覆盖四档及依据、缺口标注、受影响标注，随分析记录持久化 |

**业务规则**：

- 自有实体经项目归属到工作空间，遵循既有数据隔离约定。
- 分析记录与来源关系不物理删除，以新分析覆盖旧结论、历史记录保留的方式承载演进。
- 组织、采纳、执行与缺陷关联等解析数据不建追溯副本；采纳时点版本锚定在评审 / 计划自身的快照上。
