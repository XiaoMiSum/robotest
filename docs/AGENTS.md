# docs/AGENTS.md — 文档约定

> 本文件适用于 `docs/` 目录。总则见根目录 `AGENTS.md`，全局共享约定以总则为准。
> 本 AGENT **只负责文档相关操作**，不介入任何业务代码开发。

---

## 技术栈

- **格式**：Markdown（GFM）
- **绘图**：Mermaid（流程图/时序图/类图）
- **目录**：按业务域分 `需求/`、`概要/`、`详细设计/`、`交互设计/`、`架构/`、`spec/`
- **版本管理**：归档基线（`archive/<版本>/`）+ 工作目录迭代

## 文档架构

```
docs/
├── archive/
│   └── v1.0/                ← 已冻结的历史基线（格式模板）
├── spec/                    ← 工程规范（持续更新，不参与版本管理）
├── 需求/                     ← 需求规格说明书
├── 概要/                     ← 概要设计说明书
├── 架构/                     ← 架构设计
├── 详细设计/                  ← 详细设计说明书
├── 交互设计/                  ← 交互设计
└── AGENTS.md                ← 本文档
```

## 核心约定

| 编号 | 规则 | 检查方式 |
| --- | ---- | -------- |
| D1 | `docs/archive/` 下的所有归档文件只读，禁止修改 | 文件检查 |
| D2 | 新需求对应的工作目录无文档时，参照归档目录中对应文件格式新建 | 文件检查 |
| D3 | 文档元信息头必须包含版本、日期、状态三项 | 代码审查 |
| D4 | 进入新基线：归档当前版本 → 合并补齐归档内容 → 建新版 | 文件检查 |

## 各类型文档编写规范

### 通用要求（适用于所有文档）

- **标题**：一级标题格式为 `软件测试平台——<文档名>`，全文只允许一个一级标题。
- **元信息头**：标题下方紧跟 `**文档版本**` / `**日期**` / `**状态**`（D3），可选 `**作者**`，后接 `---` 分隔线。
- **章节编号**：二级标题起使用数字编号（`## 1. 引言`、`### 1.1 编写目的`），层级不超过四级。
- **绘图**：流程图/时序图/类图统一使用 Mermaid，禁止贴图片截图（页面结构示意可用 ASCII 字符画）。
- **术语**：首次出现的专有术语在「定义与缩写」表中给出定义；沿用上一基线术语时注明"沿用 V<版本> 定义"。
- **增量版本**：迭代版本文档只写**新增/变更**内容，已有功能不重复描述，在引言中说明与上一基线的关系；归档时再与基线合并为完整文档。
- **交叉引用**：引用其他文档时使用相对路径反引号标注（如 `docs/概要/概要设计说明书.md`）；引用同文档章节用编号（如"见 4.10"）。

### 需求文档（`docs/需求/`）

- **章节骨架**：引言（编写目的/范围/与基线关系/定义与缩写）→ 总体描述 → 功能需求 → 非功能需求 → 数据需求 → 附录。
- **功能需求条目**：每个功能点按 `**功能描述**` / `**功能点**` / `**业务规则**` 三段式编写；对应用户故事时在标题中标注编号（如 `（US-AI-001）`）。
- **只写"做什么"**：描述行为、规则、边界与验收口径，不写技术实现（表结构、接口路径、组件选型等留给设计文档）。
- **用户故事集**：按能力域分组，每条故事有唯一编号（`US-<域>-NNN`），文末维护「修订记录」。

### 概要设计（`docs/概要/`）

- **章节骨架**：引言 → 系统总体设计 → 模块划分 → 核心机制设计 → 数据设计 → 接口设计概要 → 部署视图 → 安全设计 → 设计约束与原则。
- **只做概要性描述**：定义架构、模块职责边界、核心机制、数据与接口的概要；**不写实现级细节**（框架类名、字段级设计、索引类型、中间件配置、组件 API 调用方式等一律留到详细设计）。
- **数据设计**只到实体与关系层面；**接口设计概要**只到资源与职责划分层面，不写具体路径与报文。

### 架构设计（`docs/架构/`）

- **章节骨架**：设计目标 → 仓库整体结构 → 技术选型 → 开发运行模式 → 构建流程 → 部署架构 → 关键技术实现 → 环境配置管理 → 代码规范与质量保障。
- **技术选型必须给出理由**（对比与取舍依据），选型结论需与 `docs/spec/` 工程规范保持一致。
- 目录结构使用代码块树形图表示，标注各目录职责。

### 详细设计（`docs/详细设计/`）

- **章节骨架**：引言 → 数据设计 → 接口详细设计 → 业务逻辑设计 → 前端设计 → 实施说明。
- **数据设计**：给出完整 DDL（含索引），必须符合 C5（`id`/`created_at`/`updated_at`/`is_deleted`、无物理外键）与 C9（索引规范）。
- **接口设计**：每个接口给出路径、方法、请求/响应示例（JSON 代码块）与校验规则；响应示例只展示 `data` 字段内容并在通用约定中声明；上下文标识通过请求头传递（C4），不出现在 URL。
- **错误码**：新增错误码在文档中集中定义号段，避免与既有号段冲突。
- **公共约定复用**：多份详细设计共享的约定（如 SSE 帧格式、通用响应结构）只在一份基础设施文档中定义，其余文档引用，不重复描述。

### 交互设计（`docs/交互设计/`）

- **章节骨架**：概述 → 布局设计 → 核心交互流程 → 页面设计 → 视觉与状态要求 → 页面结构示意 → 状态管理。
- **交互流程**用 Mermaid 时序图/流程图描述；**页面结构**用 ASCII 字符画示意。
- **视觉要求**引用 `docs/交互设计/视觉设计.md` 中定义的 CSS 变量与色彩体系，不另行定义颜色值。
- 覆盖空态、加载、错误、权限不足等**全部状态分支**，不只描述正常路径。

### 工程规范（`docs/spec/`）

- **规则条目化**：每条规则有唯一编号（如 C1–C9）并注明检查方式，供审查时逐条核对。
- 规范正文给出**正例与反例**代码片段，便于对照执行。
- 新增或修订规范文档后，同步更新 `docs/spec/README.md` 索引表及根目录 / 各端 `AGENTS.md` 中的引用。

### README 索引（各目录 `README.md`）

- 每个文档目录维护一份清单表：`| 文档 | 版本 | 日期 | 状态 |`，状态取值：起草中 / 已发布 / 已归档。
- 新建、归档或状态变更文档时**必须同步更新**所在目录的 README；有阅读顺序依赖时在表下用引用块说明。

## 边界

- 只修改 `docs/` 目录下的文档文件，不碰 `web/` 或 `server/` 代码
- 不介入任何业务代码开发、测试编写、构建配置等非文档任务
- `docs/spec/` 内的工程规范不参与版本归档，直接在原位更新
- 当被要求编写代码时，拒绝并告知应换用对应端（`web/` / `server/`）的 AGENT

## 文档版本生命周期

基线归档于 `docs/archive/<版本>/`，工作目录中为当前迭代版本。归档只读，当前版本在对应工作目录中修改。

| 位置 | 含义 | 可修改 |
| ---- | ---- | ------ |
| `docs/archive/<版本>/` | 已冻结的历史基线（格式模板） | ❌ 只读 |
| `docs/需求/`、`docs/概要/` 等 | 当前迭代版本 | ✅ 可改 |

### 未归档文件（原位直接修改）

以下文件无归档副本，不参与归档基线切换，直接在原位更新：

- `docs/架构/项目分层与技术架构设计.md`
- `docs/交互设计/全局导航与菜单交互系统设计.md`
- `docs/交互设计/视觉设计.md`
- `docs/详细设计/脑图组件详细设计.md`

## 文档操作

支持三种操作场景，按需选择。

### 一、同一基线内的修改

直接编辑文件内容，版本号不变，不追加变更记录。

### 二、进入新基线

当前版本的开发告一段落，需要开启下一版本时：

1. **归档** — 将工作目录中当前版本的文件复制到 `docs/archive/<当前版本>/`
2. **合并整理** — 将上一个归档版本的内容合并到新建的归档中，确保归档文档内容完整
3. **创建新版本** — 在对应的工作目录中新建文件，文件头标记新版本：

```markdown
**文档版本**：V<新版本>
**日期**：<当前日期>
**状态**：起草中
```

### 三、从归档模板新建

工作目录中无对应文档（如当前是空白目录），参照 `docs/archive/<版本>/` 中对应文件的章节结构和格式风格新建，文件头同上。

## 禁止行为

- ❌ 修改 `docs/archive/` 下的任何归档文件
- ❌ 删除归档文件
- ❌ 编写任何业务代码（这是其他 AGENT 的职责）
- ❌ 已有当前版本时仍引用归档基线做决策依据
