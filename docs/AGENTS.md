# docs/AGENTS.md — 文档约定

> 本文件适用于 `docs/` 目录。总则见根目录 `AGENTS.md`，全局共享约定以总则为准。
> 本 AGENT **只负责文档相关操作**，不介入任何业务代码开发。

---

## 格式与工具

- **格式**：Markdown（GFM）
- **绘图**：Mermaid（流程图/时序图/类图）
- **目录**：按业务域分 `00-spec/`、`01-requirements/`、`02-high-level-design/`、`03-architecture/`、`04-detailed-design/`、`05-interaction-design/`
- **版本管理**：工作目录原位迭代，历史版本经 Git 回溯
- **校验**：`bash scripts/validate-docs.sh`，Windows 无 bash 时用 `node scripts/validate.mjs --docs`（C7 提交格式 + `scripts/check-docs.mjs`：断链、行内路径、元信息、规则编号）

## 核心约定

| 编号 | 规则 | 检查方式 |
| --- | ---- | -------- |
| D1 | 文档元信息头必须包含版本、日期、状态三项 | `check-docs.mjs`（`00-spec`）+ 代码审查 |
| D2 | 工作目录无对应文档时，参照同目录同类文档的章节结构与格式新建 | 文件检查 |
| D3 | 新建、发布或状态变更文档时，同步更新所在目录的索引文件 | 文件检查 |
| D4 | 归档文件只读，禁止修改或删除 | 文件检查 |

## 各类型文档编写规范

### 通用要求（适用于所有文档）

- **标题**：除 `docs/00-spec/` 下的通用工程规范外，一级标题格式为 `软件测试平台——<文档名>`；`docs/00-spec/` 的通用工程规范使用不带项目名称的通用标题，全文只允许一个一级标题。
- **元信息头**：标题下方紧跟 `**文档版本**` / `**日期**` / `**状态**`（D1），可选 `**作者**`，后接 `---` 分隔线。**索引文件例外**：`docs/00-spec/` 及其分类索引（`00-readme.md`）必须带元信息头并受 `check-docs.mjs` 强制校验；其余目录索引（`01-readme.md`）只含标题与清单表，不写元信息头。
- **状态取值**：`起草中` / `已发布` / `已废止`，全文一致，不自造取值。
- **章节编号**：二级标题起使用数字编号（`## 1. 引言`、`### 1.1 编写目的`），层级不超过四级。
- **绘图**：流程图/时序图/类图统一使用 Mermaid，禁止贴图片截图（页面结构示意可用 ASCII 字符画）。
- **术语**：首次出现的专有术语在「定义与缩写」表中给出定义；沿用上一版本术语时注明"沿用 V<版本> 定义"。
- **增量版本**：迭代版本文档只写**新增/变更**内容，已有功能不重复描述，在引言中说明与上一版本的关系；修订直接在原位编辑，上一版本全文由 Git 历史承载，不在仓库中保留副本。
- **修改记录**：文末维护 `## 修改记录` 表格（`| 版本 | 日期 | 说明 |`）——新建时写初始行，每次修改或升版追加一行；存量文档首次修改时补建；已有「修订记录」等同类章节的沿用原章节名原位追加；索引文件不建。
- **正文连贯**：修改正文时直接改写为最终状态，变更说明一律写入文末修改记录；禁止"根据 xxx 改动""按 xx 要求新增"等变更痕迹描述，通篇读不出修改动作。
- **交叉引用**：引用其他文档时使用相对路径反引号标注（如 `docs/02-high-level-design/02-hld-overview.md`）；引用同文档章节用编号（如"见 4.10"）。

### 需求文档（`docs/01-requirements/`）

- **章节骨架**：引言（编写目的/范围/与基线关系/定义与缩写）→ 总体描述 → 功能需求 → 非功能需求 → 数据需求 → 附录。
- **功能需求条目**：每个功能点按 `**功能描述**` / `**功能点**` / `**业务规则**` 三段式编写；对应用户故事时在标题中标注编号（如 `（US-001）`）。
- **只写"做什么"**：描述行为、规则、边界与验收口径，不写技术实现（表结构、接口路径、组件选型等留给设计文档）。
- **用户故事集**：按能力域分组，每条故事有唯一编号（`US-<域>-NNN`），文末维护「修改记录」（既有「修订记录」章节沿用原章节名）。

### 概要设计（`docs/02-high-level-design/`）

- **章节骨架**：引言 → 系统总体设计 → 模块划分 → 核心机制设计 → 数据设计 → 接口设计概要 → 部署视图 → 安全设计 → 设计约束与原则。
- **只做概要性描述**：定义架构、模块职责边界、核心机制、数据与接口的概要；**不写实现级细节**（框架类名、字段级设计、索引类型、中间件配置、组件 API 调用方式等一律留到详细设计）。
- **数据设计**只到实体与关系层面；**接口设计概要**只到资源与职责划分层面，不写具体路径与报文。

### 架构设计（`docs/03-architecture/`）

- **章节骨架**：设计目标 → 仓库整体结构 → 技术选型 → 开发运行模式 → 构建流程 → 部署架构 → 关键技术实现 → 环境配置管理 → 代码规范与质量保障。
- **技术选型必须给出理由**（对比与取舍依据），选型结论需与 `docs/00-spec/` 工程规范保持一致。
- 目录结构使用代码块树形图表示，标注各目录职责。

### 详细设计（`docs/04-detailed-design/`）

- **章节骨架**：引言 → 数据设计 → 接口详细设计 → 业务逻辑设计 → 前端设计 → 实施说明。
- **数据设计**：给出完整 DDL（含索引），必须符合 C5（`id`/`created_at`/`updated_at`/`is_deleted`、无物理外键）与 C9（索引规范）。
- **接口设计**：每个接口给出路径、方法、请求/响应示例（JSON 代码块）与校验规则；响应示例只展示 `data` 字段内容并在通用约定中声明；上下文标识通过请求头传递（C4），不出现在 URL。
- **错误码**：新增错误码在文档中集中定义号段，避免与既有号段冲突。
- **公共约定复用**：多份详细设计共享的约定（如通用响应结构、错误码号段）只在一份基础设施文档中定义，其余文档引用，不重复描述。

### 交互设计（`docs/05-interaction-design/`）

- **章节骨架**：概述 → 布局设计 → 核心交互流程 → 页面设计 → 视觉与状态要求 → 页面结构示意 → 状态管理。
- **交互流程**用 Mermaid 时序图/流程图描述；**页面结构**用 ASCII 字符画示意。
- **视觉要求**引用 `docs/05-interaction-design/03-visual-design.md` 中定义的 CSS 变量与色彩体系，不另行定义颜色值。
- 覆盖空态、加载、错误、权限不足等**全部状态分支**，不只描述正常路径。

### 工程规范（`docs/00-spec/`）

- **规则登记册**：C1–C11 的唯一摘要、适用范围和检查方式维护在 `docs/00-spec/00-governance/01-overview.md`；专项规则使用 `API-`、`DB-`、`SEC-`、`UI-` 等领域前缀。
- **单一事实源**：同一主题只允许在一个主规范中定义，其他文档使用相对路径引用。
- **正例与反例**：实现规范应提供可执行或有明确标识的示例；伪代码必须标注。
- **冲突闸门**：当前实现、目标规范和设计文档冲突时，暂停并由用户确认。
- 新增或修订规范文档后，同步更新 `docs/00-spec/00-readme.md`、对应分类目录的 `00-readme.md` 及根目录 / 各端 `AGENTS.md` 中的引用。

### 目录索引

- `docs/00-spec/` 及其分类目录使用 `00-readme.md`，清单表为 `| 文档 | 职责 | 状态 |`；其他文档目录使用 `01-readme.md`，清单表为 `| 文档 | 版本 | 日期 | 状态 |`。
- 状态取值同「通用要求」；有阅读顺序依赖时在表下用引用块说明。
- 新建、发布或状态变更文档时必须同步更新所在目录的索引文件（D3）。

## 版本管理

工作目录中始终只有当前迭代版本，历史版本经 Git 回溯；若仓库中存在归档文件，则只读保存、禁止修改或删除（D4）：

| 位置 | 含义 | 可修改 |
| ---- | ---- | ------ |
| `docs/01-requirements/`、`docs/02-high-level-design/` 等业务目录 | 当前迭代版本 | ✅ 可改 |
| `docs/00-spec/` | 工程规范，原位持续维护 | ✅ 可改 |
| Git 历史 | 历史基线与旧版本全文 | ❌ 只读 |

回溯历史版本示例：

```bash
git log --follow -- docs/01-requirements/02-srs-overview.md  # 版本演进
git show <rev>:docs/01-requirements/02-srs-overview.md        # 某个版本的全文
```

## 文档操作

文档操作分四类流程，每步完成后进入下一步，禁止跳步；任一步校验失败先修复再继续。完成后必须通过「验证」一节的全部检查；提交按总则 C7 格式，一个提交只做一件事，不 push、合并走 PR。

### 操作类型速查

| 我要做什么 | 走哪个流程 |
| --- | --- |
| 工作目录中没有对应文档，从零编写 | 一、新建文档 |
| 已有文档原位增删改内容，不升版本号 | 二、修改文档 |
| 版本号递增，或状态变更（发布 / 废止） | 三、版本升级 |
| 删除、重命名、移动、拆分、合并文档 | 四、结构性调整 |

### 一、新建文档（从零编写）

1. **定位与查重**：确认文档类型（需求 / 概要 / 架构 / 详细 / 交互 / 规范）与目标目录（模块子目录按业务编号命名）；工作目录已存在对应主题文档时改走流程二，禁止另建重复文档。
2. **参照同类**（D2）：阅读同目录 1~2 篇同类文档与本文「各类型文档编写规范」中的章节骨架，确定一级标题、章节层级、元信息头与措辞风格。
3. **起草**：
   - 一级标题 `软件测试平台——<文档名>`（`00-spec/` 通用规范除外），全文唯一；
   - 标题下紧跟元信息头 `**文档版本**：V1.0` / `**日期**：<当天>` / `**状态**：起草中` + `---` 分隔线（索引文件按「目录索引」规则例外）；
   - 按类型章节骨架成文，数字编号、层级不超过四级；功能需求条目用三段式；只写"做什么"，不写技术实现；
   - 文末建 `## 修改记录` 并写入初始行（索引文件例外）；
   - 交叉引用只用相对路径反引号标注；上层文档不引用下层文档（工程规范与需求不引用详细设计、交互设计）。
4. **登记索引**（D3）：在所在目录索引新增清单行；新建模块子目录时同步外层索引；`00-spec/` 新增规范还需同步分类 `00-readme.md` 与相关 `AGENTS.md` 引用。
5. **校验**：`bash scripts/validate-docs.sh` 必须 exit 0（本端专属，不运行其他端脚本）。
6. **提交**：按 C7 格式提交本文件及其索引登记。

### 二、修改文档（同一版本内原位迭代）

适用：勘误、按实际实现对齐、增删章节但不升版本号。

1. **确认边界**：仅修改目标文件；D4 归档文件与 Git 历史基线禁止改动。
2. **原位编辑**：版本号与状态保持不变；正文直接改写为最终状态、上下文连贯，禁止"根据 xxx 改动"等变更痕迹描述（见「通用要求·正文连贯」）。
3. **追加修改记录**：文末「修改记录」表格追加一行（版本 / 日期 / 说明，说明本次改动要点）；存量文档首次修改时先补建章节与初始行，已有同类章节的原位追加。
4. **联动检查**：内容涉及行为、规则或路径变化时，全局检索引用点（链接、行内反引号路径、索引清单、分册-章节对照表）并一并更新；删除条目前先确认无处依赖。
5. **登记索引**：日期或状态有变则同步索引（D3），未变则索引不动。
6. **校验与提交**：同流程一的第 5、6 步。

### 三、版本升级（发布 / 修订升版 / 状态变更）

1. **更新元信息头**（D1）：`**文档版本**` 递增（Vx.y）、`**日期**` 为当天、`**状态**` 改为 `已发布` 或 `已废止`。
2. **追加修改记录**：文末「修改记录」表格追加一行，说明本次升版内容。
3. **升版正文**：按「增量版本」要求只写新增或变更内容，已在引言说明与上一版本的关系；已有功能不重复描述。
4. **同步索引**（D3）：所在目录索引的版本、日期、状态三列同步更新；`00-spec/` 规范还需同步分类 `00-readme.md` 与相关 `AGENTS.md` 引用。
5. **校验与提交**：同流程一的第 5、6 步；旧版本全文由 Git 历史承载，仓库不留副本。

### 四、结构性调整（删除 / 重命名 / 移动 / 拆分 / 合并）

1. **检索引用**：全局检索目标文档的路径与锚点（链接、行内反引号路径、索引清单、对照表），列出全部引用点后再动手。
2. **执行调整**：
   - 重命名 / 移动：用 `git mv` 保留历史，逐一替换旧路径；
   - 删除：清除或改指全部引用，被删主题不得再被引用为决策依据；
   - 拆分 / 合并：原位置留指针段指向新位置；拆出章节重排编号前先确认无锚点与编号互引；合并时消除重复描述，同一主题只保留单一事实源。
3. **登记索引**（D3）：索引清单与分册-章节对照表同步增删行；正文被改动的文档按流程二第 3 步追加修改记录（纯重命名 / 移动不记）。
4. **校验与提交**：同流程一的第 5、6 步；`check-docs` 必须确认无断链与旧路径残留。

## 边界

- 只修改 `docs/` 目录下的文档文件，不碰 `web/` 或 `server/` 代码
- 不介入任何业务代码开发、测试编写、构建配置等非文档任务
- `docs/00-spec/` 内的工程规范直接在原位更新，不做版本归档
- 当被要求编写代码时，拒绝并告知应换用对应端（`web/` / `server/`）的 AGENT

## 验证

提交前必须运行本端验证脚本，任一失败先修复再提交：

```bash
bash scripts/validate-docs.sh   # 本端（C7 提交格式 + 文档专项检查）
bash scripts/validate.sh --all  # 全量编排（人工 / CI，含前后端质量门禁）
```

Windows 无 bash 时改用等价命令（同一实现 `scripts/validate.mjs`）：

```powershell
node scripts/validate.mjs --docs
node scripts/validate.mjs --all
```

`check-docs.mjs` 执行四类检查：

1. **链接与锚点**：相对链接断链、旧锚点；
2. **行内路径**：反引号内 `docs/`、`scripts/`、`.github/` 前缀与 `*.md` 路径的存在性；
3. **元信息**：`docs/00-spec/` 下每篇文档前 12 行内的版本（Vx.y）、日期（YYYY-MM-DD）、状态三项；
4. **规则编号**：`C*` 与 `UI-*` 规则号必须已登记于 `docs/00-spec/00-governance/01-overview.md` 的规则登记册。

## 禁止行为

- ❌ 在仓库中重建归档目录或复制文档保存历史版本（历史版本一律走 Git）
- ❌ 修改或删除 Git 历史中的既有基线
- ❌ 编写任何业务代码（这是其他 AGENT 的职责）
- ❌ 引用已删除的文档或不存在的路径作为决策依据
- ❌ 只改文档不更新所在目录索引（D3）
- ❌ 在正文写"根据 xxx 改动""按 xx 要求新增"等变更痕迹描述（变更说明只写入文末修改记录）
