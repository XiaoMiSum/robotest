# 构建与部署规范

**文档版本**：V1.0
**日期**：2026-09-24
**状态**：已发布

---

## 1. 适用范围

本文定义项目通用的构建、环境、发布、回滚和交付要求。

具体项目的实际命令、端口、环境文件、脚本和发布步骤不在本文维护，统一参考项目部署 Runbook。

质量门禁见 `07-quality.md`，安全基线见 `10-security.md`，数据库迁移原则见 `06-database.md`。

## 2. 构建原则

### 2.1 可重复构建

- 依赖必须通过锁文件或 BOM 固定。
- 构建环境必须记录 Node、pnpm、Java、Maven 和关键镜像版本。
- 同一 commit 在相同配置下必须能够生成等价制品。
- 构建不得依赖未声明的本机工具、全局变量或手工文件。
- 构建结果必须能够追溯到 commit、构建参数和依赖版本。

### 2.2 构建阶段

通用构建至少包括：

```text
依赖安装
→ 静态检查
→ 类型检查
→ 单元/集成测试
→ 契约检查
→ 编译
→ 制品生成
→ 制品校验
```

质量门禁的实际阈值和工具以 `07-quality.md` 及 CI 配置为准。

### 2.3 制品要求

制品必须：

- 有唯一版本或 commit 标识；
- 包含构建时间和依赖信息；
- 不包含开发环境密钥；
- 经过完整性校验；
- 能够被部署环境重复识别；
- 在发布前保存构建日志和校验结果。

## 3. 环境配置原则

### 3.1 环境隔离

- dev、test、prod 配置必须隔离；
- 环境差异通过 profile、环境变量或密钥管理服务注入；
- 不得通过修改已提交配置文件切换生产环境；
- 不得把测试环境配置复制到生产环境；
- 每个环境必须有明确的负责人、地址、数据库和 Redis 信息。

### 3.2 密钥管理

以下内容必须通过环境变量或密钥管理服务注入：

```text
数据库凭据
Redis 凭据
JWT/认证密钥
加密密钥
第三方服务密钥
```

生产环境缺少关键配置时必须启动失败，不能回退到开发默认值。

### 3.3 配置校验

发布前必须校验：

- 必需环境变量存在；
- 密钥格式和长度符合要求；
- 数据库和 Redis 可连接；
- 端口和 URL 来自目标环境；
- Mock、调试和公开接口开关符合环境策略；
- 生产环境没有默认密码、Token 和测试证书。

## 4. 部署方案原则

项目可以选择以下部署方式：

| 方案 | 原则 |
| --- | --- |
| 独立部署 | 前后端分别构建、发布和扩缩容 |
| 合并部署 | 前端静态资源随应用制品一起发布 |

无论采用哪种方案，都必须：

- 明确制品来源；
- 明确数据库迁移顺序；
- 明确健康检查和就绪检查；
- 明确回滚方式；
- 明确发布后验证责任人；
- 明确静态资源和 API/WebSocket 路由边界。

## 5. 数据库发布原则

发布顺序必须遵循：

```text
备份
→ 兼容性迁移
→ 应用发布
→ 数据验证
→ 健康检查
→ 观察
```

要求：

- 已部署环境不得重复执行全量初始化脚本；
- 迁移必须可追踪版本；
- 大表迁移必须评估锁表和执行时间；
- 数据库回滚不能依赖未经验证的逆向 SQL；
- 迁移失败必须有停止、恢复和人工介入方案。

## 6. 发布门禁

发布前必须确认：

- [ ] 质量门禁全部通过；
- [ ] 构建制品可重复生成；
- [ ] 依赖漏洞、Secret 和许可证扫描通过；
- [ ] 数据库迁移和回滚方案已确认；
- [ ] 生产配置完整且无默认密钥；
- [ ] 健康检查、就绪检查和核心链路可用；
- [ ] 版本、变更内容和回滚负责人已记录。

发布模式不得使用跳过 lint、类型检查、测试或契约校验的参数。

## 7. 发布后验证

通用发布后验证至少包括：

- 应用健康检查；
- 数据库和 Redis 连接检查；
- 认证和 Token 流程；
- 关键 API 响应和错误处理；
- 权限和租户隔离；
- 实时连接（如项目启用）；
- 日志、指标和审计；
- 数据迁移结果；
- 回滚开关和联系人。

具体项目的命令和 smoke test 由项目 Runbook 维护。

## 8. 回滚原则

- 应用回滚必须兼容已执行的数据库迁移；
- 制品必须保留上一个稳定版本；
- 回滚前记录当前版本、数据库版本和异常现象；
- 回滚后重新执行健康检查和核心链路验证；
- 回滚失败时进入人工事故处理流程；
- 事故和回滚结果必须形成记录。

## 9. CI 边界

CI 的质量门禁由 `07-quality.md` 定义，发布编排由项目 Runbook 维护。两者不得各自维护一套不同的 lint、测试、覆盖率或安全扫描规则。
