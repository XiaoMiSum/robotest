### 1.4 定义与缩写

| 术语 | 定义 |
| ---- | ---- |
| vision 能力 | 模型配置 `capabilities` 中的 `vision` 标签，声明模型可理解图片输入 |
| 媒体直传 | 图片字节经 Spring AI `UserMessage + Media` 随消息直接送入模型，不经图片 → 文本中间转换 |
| 能力选型 | 解析模型时按调用所需能力（如 `vision`）过滤候选，并按 `priority` 升序取首 |
| 必需能力 | 由任务输入派生的本次调用不可缺少的能力标签（`vision` 或无） |

## 2. 开发方案

### 2.1 现状分析

#### 2.1.1 模型解析与选型

- 解析为两级定点：任务行 `model_id`（存在且启用）→ 全局默认模型（启用），执行期同口径复解析；无任何按 `capabilities` 的过滤。
- `priority` 仅用于管理端模型列表升序展示；不存在「默认模型失效时按 priority 升序尝试」的兜底循环，调用失败直接映射为模型服务调用失败（1000018117）并置执行终止（现状代码仍为任务失败态，随 AI Task 迁移对齐），重试复用同一模型（Spring AI 内建重试）。
- 任务提交时解析并回写 `model_id`（提交时解析、执行不漂移）；该回写当前不含能力语义。
- `capabilities` 字段在保存 / 更新时校验取值受控，运行期零读取。

#### 2.1.2 多模态消息构造

- 模型调用门面 `AiModelClient` 的 `buildPrompt` 已支持媒体：`media` 为空构造纯文本 `UserMessage`，非空则构造 `UserMessage + Media(mimeType, bytes)`，并有单测覆盖。
- 任务侧门面 `TaskExecutionContext.chat(systemPrompt, userPrompt, media)` 已暴露三参多模态重载；当前为**单媒体**形态（每次至多 1 张）。

#### 2.1.3 助手多模态现状

- 发送载荷仅 `content`（Markdown ≤4000 字符）+ `attachments`（业务实体引用：需求 / 模块 / 脑图文档 / 用例 / 评审 / 计划）；「附件」是数据引用而非文件。
- 输入区无任何图片 / 文件上传控件；消息表无图片字段；`assistant_parse` 任务的判别段与回答段调用均为纯文本。
- 图片基建已完备：泛化文件模块（`POST /files` → 稳定路径 `/api/files/{id}/download` → 访问 URL 换签）与 Markdown 图片换签渲染可直接复用。

#### 2.1.4 AI 任务多模态现状

| 任务域 | 图片入模现状 |
| ---- | ---- |
| 需求导入 `requirement_import` | **唯一消费点**：图片扩展（png / jpg / jpeg / gif / webp / bmp）时文档正文留空，文件字节经 `AiChatMedia` 随消息直传；md / docx 走文本抽取 |
| 缺陷分析（分类 / 派生 / 趋势 / 重复扫描） | 四任务上下文均为纯文本（标题、步骤、等级、统计）；缺陷附件（截图）有独立存储与下载通道，从未被 AI 处理器读取 |
| 辅助功能（用例补全 / 等级建议 / 计划排序） | 纯文本清单调用，无图片输入 |
| 生成链 / 覆盖分析 / 助手解析 | 纯文本调用 |

- 需求导入图片直传**无能力校验**：默认模型未声明 `vision` 时照样发图，失败由供应商报错兜底为 1000018117，用户得不到「需配置视觉模型」的明确指引。

#### 2.1.5 用量与管理端

- 用量 `call_type` 仅 `chat / embedding` 两值，带图调用无从区分；多模态调用的 `prompt_scene` 可定位场景但不指示是否携图。
- 管理端能力复选框可勾选 `vision`，但模型列表不展示能力列、不支持按能力筛选，管理员无法直观识别视觉模型。

### 2.3 vision 智能路由设计（③ 基础机制）

#### 2.3.1 解析规则

`AiSettingsReader` 解析入口扩展为**带必需能力的两级 + 扫描**：

```
resolveModel(preferredModelId, requiredCapability):
  1. preferredModelId 存在、启用、且（requiredCapability 为空或 capabilities 包含之）→ 返回
  2. 全局默认模型启用、且满足能力 → 返回
  3. requiredCapability 非空：启用且 capabilities 包含该能力的模型按 priority 升序 → 取首个
  4. 无候选 → null（调用方映射错误码）
```

- `requiredCapability` 为空时语义与现行两级解析完全一致，纯文本调用行为不变。
- `priority` 在第 3 步兑现「能力选型内的兜底顺序」（裁决点 D2-A）。

#### 2.3.2 必需能力的派生

类型适配器（TypeAdapter）声明 `requiredCapability(input)`（缺省返回无），由提交与执行两条路径共同调用；判定依赖项目范围的任务（`bug_classify` 批量）声明带上下文重载 `requiredCapability(input, context)`（缺省委托前者）：

| 任务 | 派生规则 |
| ---- | ---- |
| `requirement_import` | 输入 `fileId` 对应文件扩展为图片 → `vision`（文件已在提交前上传，可查元数据判定） |
| `assistant_parse` | 消息带图片 → `vision`（消息先落库再提交，读消息即知） |
| `bug_classify` | 草稿 `fileIds` 非空或批量解析后的缺陷集存在图像类附件 → `vision`（2.5.2；批量按项目解析缺陷集，仅查附件元数据不读字节） |
| 其余任务 | 无（行为不变） |

- **提交期**：`createTask` 用 `resolveModel(null, capability)` 解析并回写 `model_id`，保持「提交时解析、执行不漂移」。
- **执行期**：`AiTaskExecutor` 用 `resolveModel(task.modelId, capability)` 复验——默认模型被停用 / 换人后仍保证能力安全，不会把图片发给无视觉能力的模型（AI Task 迁移后由 Agent 执行核承接）。

#### 2.3.3 降级与错误码

- 提交期无候选：直接业务异常、**快速失败**，不静默丢图（对齐概要 4.6「不降级为无引用生成」的取向——图片是用户意图的核心输入，忽略即失真）：
  - 底座新增 `1000018124`「未配置支持视觉能力的已启用模型，请在配置中心启用」（底座号段 1000018101–1000018150，现行至 1000018123，新增顺延）。
- 执行期无候选（候选被停用等罕见情形）：执行终止并携带同一错误码。
- 纯文本调用缺模型仍为现行 1000018118，不改。

### 2.4 助手多模态设计（①）

#### 2.4.1 数据与接口

- 消息表 `ai_assistant_message` 补列 `images jsonb NULL`（存量行为空，逻辑删除与通用列照旧，符合 C5；迁移以「补列 + 列注释」交付，不重建表）：元素 `[{ fileId, name }]`。
- 发送请求补字段 `images`：`[{ "fileId": "…" }]`（单条 ≤3 张，服务层校验、DTO 不做注解约束）；校验文件存在、类型属图片白名单（png / jpg / jpeg / gif / webp / bmp，与需求导入一致）、单张 ≤10MB（与正文贴图一致），违反为新增 `1000018264`「图片附件非法」（助手号段 1000018251–1000018279，1000018263 为会话归属空间校验占用）。
- 上下文头分层不变（C4）：发送带 `X-Active-Workspace`，图片为平台级文件资源 ID，随请求体传递、不入 URL。

#### 2.4.2 调用链

1. 前端经泛化文件模块上传图片取得 `fileId`，随消息提交；
2. 服务端校验 → 消息落库（正文 + 实体引用 + 图片）→ 提交 `assistant_parse`（图片非空 ⇒ 必需能力 `vision`，经 2.3 路由解析并回写 `model_id`）；
3. 处理器读回图片字节（复用文件模块读取），判别段与回答段调用统一携带媒体：图片经媒体列表化（裁决 D6-A）构造后随同一 `UserMessage` 发送（单图与多图同一路径）；
4. 无视觉模型的失败发生在提交期（HTTP 业务错误，前端内联提示），执行期模型失效经既有 SSE `error` 事件透传。

#### 2.4.3 前端

- 输入区（ComposerInput）新增图片按钮，与实体附件（回形针）并列；选择即上传，展示缩略图 chip（可删除）；预校验张数 / 类型 / 大小。
- 用户消息渲染图片缩略图，经既有换签机制取访问 URL，加载失败复用占位。
- 草稿暂存、流式禁用、Enter 发送等既有状态分支不变。

### 2.5 AI 任务多模态设计（②）

#### 2.5.1 需求导入（本期收口）

- 直传链路复用，仅接入 2.3 的必需能力派生：图片文件 ⇒ 提交期选 `vision` 模型并回写；无视觉模型 ⇒ 1000018124 快速失败（替代现行「执行期供应商报错 → 1000018117」的模糊指引）。
- 页面交互无变化；失败文案由新错误码承载，任务详情与提交错误提示透出。

#### 2.5.2 缺陷分析（裁决 D4：纳入本期）

- **任务分型口径**：仅 `bug_classify`（草稿建议与批量分类）入模截图——分类对重现步骤与界面状态最敏感；派生（triage）、趋势（trend）、重复扫描（duplicate）维持纯文本（统计与文本相似度为主，图片无增量）。
- **附带上限**：每缺陷取图像类附件（png / jpg / jpeg / gif / webp / bmp）≤2 张；批量任务图片总量 ≤8 张，按缺陷序截断，超出部分仅文本；随附图片与缺陷块的对应关系在提示词中显式标注（防上下文膨胀与图文错配）。
- **能力派生**：草稿 `fileIds` 非空（提交期已校验为图像白名单）或批量解析后的缺陷集存在图像类附件 ⇒ 必需 `vision`；批量判定按项目解析缺陷集、仅查附件元数据（不读字节），模型选型与无视觉模型快速失败统一走 2.3.2 与 1000018124。
- **读取通道**：后端直接读缺陷附件存储取得字节（与下载同源），不依赖泛化文件模块迁移与前端换签；缺陷附件与泛化文件模块的统一迁移按主计划文件管理改造另行推进，不构成本项前置。
- **关联详设**：`docs/04-detailed-design/07-ai-capability/05-ai-defect-analysis.md` 补截图入模口径（输入字段、上限、失败语义复用 1000018124）。

#### 2.5.3 辅助功能与生成链（本期不接入）

- 输入为用例清单、计划条目与文档正文等文本上下文，RAG 检索主导；图片直传仅在需求导入已被证明必要。维持纯文本口径，相关详设不变更。
- 概要 4.5「多模态解析」口径按裁决 D1 处置后，此处引用其结论、不重复定义。

## 4. 风险与应对

| 风险 | 影响 | 应对 |
| ---- | ---- | ---- |
| 管理员能力声明与模型实际不符（标了 vision 实际不支持） | 调用期供应商报错，执行终止 | 失败映射既有 1000018117 并透出供应商摘要；后续可为连通性测试扩展「带图测试」 |
